# 任务内动态子代理（Task Subagents / Fan-Out Delegation）需求评估与技术方案设计

> 状态：**规划与设计定案**
> 制定日期：**2026-11-10**
> 关联需求：**在多模型项目小组（Team）与单兵模式执行任务时，解决单任务内串行探索耗时过长、网络往返累积慢的瓶颈，允许 Agent 根据任务复杂度与探索范围，动态派生多个只读轻量子代理（Subagents）并发探索、排查与总结，以“单轮并发”取代“数十轮串行”，大幅压缩任务耗时并降低主上下文噪音。**

---

## 1. 背景分析与核心痛点

### 1.1 现状与执行瓶颈

在当前 Orcsy 架构中，系统已在**宏观层面**实现了两个维度的并行能力：
1. **调度层（Scheduler）**：支持多项目通过 `max_parallel_agents` 线程池并发执行；
2. **项目小组层（Project Team）**：PM 拆分出的无依赖子任务，支持通过 `parallel_worktree` 在多个独立 Git Worktree 沙盒中并发开工。

然而，在**微观单个任务的执行内部**，执行器始终采用**完全单线程的串行对话循环（Serial Turn Loop）**：
```
[大模型生成思考 (10~25s)] 
        ▼
[调用单一工具 (0.5~2s)] 
        ▼
[工具返回单条结果，追加进 messages] 
        ▼
[大模型再思考 (10~25s)] 
        ▼
[调用下一个工具...]
```

### 1.2 导致“慢”的 3 大根本原因

以真实任务中 PM 探索拆解一个中型全栈项目（如 `pixsy`）为例：
1. **串行网络往返与推理延迟累加**：
   - PM Agent 前后调用了 22 轮工具（`list_dir` → `grep` → `read_file` × N → `find_files` × N...）；
   - 哪怕每次工具本身执行只需要 0.05 秒，但 22 次 HTTP 往返加上大模型生成思考与 Token 耗时（平均每次 15 秒），**单任务串行耗时直接累积达到 4~5 分钟**。
2. **主对话上下文被巨量噪音稀释（Context Pollution）**：
   - 串行探索期间读取的每个文件、每一次 grep 命中清单都会逐轮堆积在主 Agent 的 `self.messages` 历史中；
   - 即使内置了 `_trim_context` 滚动占位压缩，早期的探索细节仍会大量吞噬 Token 预算，并导致注意力分散，影响最终架构决策精度。
3. **人类研发者的真实行为是“分工或并发摸底”**：
   - 真实工程师在面临一个大功能时，往往会并排打开多个编辑器标签页、或者由主架构师安排两位助理“你去看看前端组件怎么写，你去看下后端数据表怎么设计”，同时开工摸底并在 1 分钟后汇总结论，而不是一个人按顺序排队排查。

## 2. 核心架构设计：任务内动态子代理（Subagent Fan-Out）

### 2.1 概念对比：任务拆分 vs 动态子代理

明确两者的职责边界，严禁概念混淆：

| 维度 | 宏观任务拆分 (`create_tasks`) | 任务内动态子代理 (`delegate_explore`) |
| :--- | :--- | :--- |
| **生命周期** | **持久化落盘**：生成物理 `.md` 任务文件，进入项目任务队列 | **内存临时生命周期**：仅在当前任务单轮内部并发运行，收敛后即销毁 |
| **执行载体** | 独立的专职角色（后端、前端、QA），在独立 Git Worktree 分支修改代码并等待审查 | 纯**只读轻量子代理**（Subagent），在当前工作区并发读取/检索/分析代码 |
| **产出结果** | 代码变更、Git 提交、单元测试、待合并主分支 | **高度提炼的结构化 Markdown 调研报告**，直接喂给主 Agent |
| **适用场景** | 确定需要多端接力开发、跨角色联调交付的业务需求 | 主任务刚启动时摸底架构、定位排查、对比竞品或交叉检索依赖 |

### 2.2 执行流模型

```
           ┌──────────────────────────────────────────────┐
           │        主 Agent (Main Task Agent, 如 PM)      │
           └──────────────────────┬───────────────────────┘
                                  │ 调用工具 delegate_explore({ subagents: [...] })
                                  ▼
           ┌──────────────────────────────────────────────┐
           │           SubagentRunner (并发调度器)          │
           │  - 线程池并发 (ThreadPoolExecutor)            │
           │  - 共享父任务 stop_event (秒级强制停止)        │
           │  - 继承只读探索工具集 (list_dir/read/grep)     │
           └──────────────┬───────────────┬───────────────┘
                          │               │
            ┌─────────────┴─────┐   ┌─────┴─────────────┐
            ▼                   ▼   ▼                   ▼
       [子代理 1: 后端探索]    [子代理 2: 前端探索]    [子代理 3: 测试基建摸底]
       - 独立精简 prompt      - 独立精简 prompt      - 独立精简 prompt
       - 并发读 internal/     - 并发读 web/src/       - 并发读 *_test.go
       - 独立完成 2~4 轮       - 独立完成 2~4 轮       - 独立完成 2~4 轮
       - 提炼关键数据模型与路由 - 提炼关键路由与状态   - 提炼现有测试规范
            │                   │                       │
            └─────────────┬─────┴───────────────────────┘
                          │ 汇总生成精炼报告 (Markdown 结构化)
                          ▼
           ┌──────────────────────────────────────────────┐
           │ 报告以单条 Tool Result 返回给主 Agent:        │
           │ "【子代理并发探索完成】：                       │
           │  1. 后端摸底：/api/v1/admin 架构...          │
           │  2. 前端摸底：AdminView.vue 路由...          │
           │  3. 测试摸底：go test 验收套件..."          │
           └──────────────────────┬───────────────────────┘
                                  │ 主 Agent 在第 2 轮即可直接基于全景信息完成高精度决策/拆单
                                  ▼
                     [快速交付 finish / create_tasks]
```

**耗时对比**：
- 原有逻辑：22 轮串行探索，耗时约 **240 秒**；
- 动态子代理：1 次派发（3 个小助理并发执行 3 轮，并行时间约 25 秒）+ 1 轮主 Agent 总结，**总耗时压缩至 35~40 秒，提速 6 倍**！

## 3. 具体技术设计

### 3.1 工具协议定义 (`delegate_explore`)

在 `orcsy/tools.py` 中新增 `delegate_explore` 工具：

```python
{
    "type": "function",
    "function": {
        "name": "delegate_explore",
        "description": "并发派生多个轻量只读子代理替自己去探索项目的不同模块或排查问题。子代理并行阅读检索后，系统会自动将各子代理的调查摘要汇总返回给你。适合大范围代码摸底、跨端架构调研或对比排查，大幅减少单兵逐轮阅读的轮数与耗时。",
        "parameters": {
            "type": "object",
            "properties": {
                "subagents": {
                    "type": "array",
                    "description": "子代理任务清单（建议 2~4 个，最多 4 个）",
                    "items": {
                        "type": "object",
                        "properties": {
                            "name": {
                                "type": "string",
                                "description": "子任务简短标题（如「调研后端用户数据模型」）"
                            },
                            "focus": {
                                "type": "string",
                                "description": "子代理需要调研的核心关注点与需要回答的问题"
                            },
                            "paths": {
                                "type": "array",
                                "items": {"type": "string"},
                                "description": "建议子代理重点关注的相对文件或目录路径（可选）"
                            }
                        },
                        "required": ["name", "focus"]
                    }
                }
            },
            "required": ["subagents"]
        }
    }
}
```

### 3.2 子代理执行引擎 (`SubagentRunner`)

新建 `orcsy/subagent.py`：
1. **轻量上下文构建**：
   - 系统提示词：简短明确的只读调研员指令（“你是专职代码调研员，任务是针对指定关注点进行快速探索，提取关键数据结构、接口与文件路径，在 3~5 轮内调用 finish 输出结论，严禁冗长叙述”）；
   - 工具集：**严格限定为只读工具**（`list_dir`、`find_files`、`read_file`、`grep`、`read_skill`、`finish`），严禁包含任何文件写入、命令执行或二次派生工具。
2. **并发控制与线程池**：
   - 使用 `concurrent.futures.ThreadPoolExecutor(max_workers=len(subagents))`；
   - 绑定父任务的 `stop_event`：主任务一旦被用户在看板强制停止，所有在途子代理在当前请求/工具边界立即安全退出。
3. **输出收敛与报告格式化**：
   - 子代理完成时调用 `finish(summary=..., notes=...)`；
   - `SubagentRunner` 收集所有子代理的 `summary` 与 `notes`，拼接成格式优美的 Markdown 综述：
     ```markdown
     ### 🔍 动态子代理并发探索报告（共 3 项任务全部完成）：
     
     #### 1. 调研后端用户数据模型 (完成，用时 12s)
     - **核心文件**：`internal/model/users.go`, `internal/api/api.go`
     - **发现摘要**：用户表已有 `Role` 字段，缺失管理员批量分页接口；已存在 `CountUsers` 方法。
     
     #### 2. 调研前端管理后台现状 (完成，用时 15s)
     - **核心文件**：`web/src/views/AdminView.vue`, `web/src/router/index.ts`
     - **发现摘要**：后台目前仅有站点设置面板，需新增用户表格与抽屉编辑组件。
     ```

## 4. 安全防护与熔断机制 (Guardrails & Circuit Breakers)

引入子代理机制时，必须严防 Token 风暴与递归失控。系统实施以下 **5 重安全熔断**：

| 熔断门禁 | 机制规则 | 彻底防御的风险 |
| :--- | :--- | :--- |
| **F1 递归深度锁死** | 子代理的可用工具集**坚决剔除** `delegate_explore` 与 `create_tasks`，`depth` 严格限制为 1 | 杜绝“子代理派生孙代理、孙代理派生曾孙代理”的无限递归死锁与指数级 Token 消耗 |
| **F2 扇出数量上限** | 单次 `delegate_explore` 最多允许派生 **4 个**子代理；单个主任务全生命周期内最多允许调用 **2 次**该工具 | 防止模型一次性盲目召唤几十个子代理引发并发线程耗尽与服务商 API 限流 (429) |
| **F3 单子代理轮数熔断** | 每个子代理的 `max_turns` 强制限制为 **6 轮**（远低于主任务的 40 轮） | 子代理定位为“快速摸底”，若 6 轮未完则强制收敛输出当前已有发现，防止卡死 |
| **F4 严格只读隔离** | 子代理仅放行只读探索工具，不分配 Worktree，严禁写文件与跑命令 | 保证子代理的任何行为零副作用，不会污染或破坏主仓库代码 |
| **F5 统一强停与用量记账** | 子代理的 prompt/completion tokens 实时累计并入父任务台账，且直接受看板「强制停止」信号管控 | 用户点击强停时所有子代理 0.2 秒内全部同步打断，台账数据分毫不漏 |

## 6. 预期收益与验收指标

1. **探索耗时指标**：PM 针对 10 个以上代码文件的大任务拆解，探索阶段耗时由 4~5 分钟**降至 45 秒以内**；
2. **Token 经济性指标**：主 Agent 上下文消息轮数减少 60% 以上，消除早期冗余的文件全文重复计费；
3. **稳定性指标**：子代理支持超时自动收敛与一键秒级打断，零并发锁冲突，单元测试 100% 通过。
