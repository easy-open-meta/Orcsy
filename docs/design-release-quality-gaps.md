# 四阶段发布流程评估：Claude Code 团队 × Orcsy 现状与缺口

> 状态：**评估稿，仅文档，不落地代码**｜2026-11-23
> 来源：Anthropic《How the Claude Code team does code review》整理版的四阶段流程。
> 目标：逐阶段对照 Orcsy 已具备 / 缺失的能力，给出可补强清单与优先级，
> 供后续排入路线图（不在此文档外改动任何代码）。

## 0. 一句话结论

Orcsy 在「写代码自动化」上已经很靠前（拆单 / 开发 / 联调 / 审查 / 提交），
但在 Claude 四阶段流程强调的「**审核与质量才是瓶颈**」这一面还有明显结构空位：
**机器门禁偏弱、人工审批是二元的、合入前缺重测、发布后缺分级与快速回滚**。
建议优先补：② 风险分级审批 + AI 审核结构化、③ 合入前在最新主分支重测、
④ 更新通道分级（latest / stable）。

## 1. 四阶段流程速览（评估基准）

> 一个 Bug 要闯 10 关：AI 跑测试 → 新 Agent 查质量 → CI → AI 审核 → 安全审核 →
> 风险审批 → 合并队列 → 功能开关 → latest → stable → 观察/回滚。
> 核心原则：**人负责关键决策，AI 负责大量执行（Human steers, agents execute）。**

| 阶段 | 关键动作 | 一句话本质 |
| --- | --- | --- |
| ① PR 前 | AI 自己跑起来（截图/看网页）；空白上下文的新 Agent 查质量 | 先证明能跑，再谈质量 |
| ② PR 中 | CI → AI 审核（找/筛/处理）→ 安全审核 → 按风险分级审批 | 机器先行，人只审重要改动 |
| ③ 合并时 | 合并队列：与最新 main 合并后重测，通过才真合入 | 拦下组合回归，main 始终可跑 |
| ④ 合并后 | 功能开关先藏 → latest 尝鲜 → 一周后推 stable → 观察/回滚 | 安全到达用户，出事能快退 |

## 2. Orcsy 现状对照（逐阶段）

### 2.1 ① PR 前：先能跑，再查质量

**Claude 要点**：开发 Agent 自己把产品跑起来（跑程序、看网页、截图、操作电脑）；
用一个**全新上下文**的 Agent 只拿「目标 + 改动」做客观质量判断。

**Orcsy 已有**：
- `local_debug`（CDP 驱动 Chrome/Edge、截图、后台服务管理）、QA 只读验证角色、`review` 独立模型。
- Review Agent 走独立 `review.llm` 且强制与任务模型不同（`assert_review_model_distinct`）。

**缺失 / 可补强**：
1. 「可运行性」不是强门禁：当前 `completed` 主要看 `files_changed`（PM 完成声明校验刚补了
   「create_tasks / 文件变更证据」），但**没有强制「运行成功 + 截图/日志」作为完成证据**。
   → 建议把 QA 只读验证与 `local_debug` 的截图/运行日志升为「完成前必须附证据」的一环（底座已有）。
2. Review Agent 的「空白上下文」约束不显式：现在是给 diff + 任务，但没有刻意剥离写码过程。
   → 建议在审查提示词里明确「只看目标 + 变更 diff，不注入原任务执行过程」，保持客观。

### 2.2 ② PR 中：四道关卡，机器先行（**缺口最集中**）

**Claude 要点**：CI；AI 审核三分类逐条处置且「未处理→不能继续」；安全审核独立一轮不清零不合；
按风险分级审批（低 0 人 / 中 1 人 / 高 2 人）。

**Orcsy 已有**：
- 测试执行：开发/审查 Agent 可跑 `pytest`（Docker 镜像内置 pytest）——但没有独立「CI 门禁」。
- Review Agent：独立模型 + diff 审查 + 返工上限（`max_review_rounds`）——但没有「三分类、逐条处置、收口」结构。
- 安全：0.31.0 新增 `security` 只读角色（变更范围静态扫描 + 依赖 CVE 检索）——**可选角色，非默认门禁**。
- 人工审批：人工把关提交——**单一且二元**（所有代码同等对待，无风险分级）。

**缺失 / 可补强（按价值排序）**：
1. **风险分级审批（最值得做）**：把现有人工把关提交从「一刀切」升级为按**改动对象**分级：
   - 低风险（文档/前端样式/技能库）→ 自动通过；
   - 中风险（普通业务逻辑/接口）→ 项目 owner 1 人；
   - 高风险（计费/自更新/升级/配置迁移/`egress`/CI/打包脚本）→ 2 人双重确认或显式二次校验。
   人只看重要改动，注意力聚焦（与「Human steers」一致）。
2. **AI 审核结构化**：审查结论按「重要 / 小 / 已有」三分类，逐条处置；**有未处理的重要问题 →
   不通过**。收口规则挂到现有 `review_max_rounds` 上：第 N 轮只看新 diff、同类问题一次说全、
   不重复提已有意见。一轮通过率可作为质量度量。
3. **CI 门禁**：任务提交/合并前跑 lint + 类型检查 + 构建 + 测试，事件与结果进 runlog（复用 `run_command`
   与 Docker 内置工具链；离线环境剪掉联网类步骤）。补强「机器先拦一遍」。
4. **安全门禁默认化**：把 `security` 从可选角色提为「合并前的默认独立一轮」——至少两项：
   改动范围的密钥/敏感值扫描（复用 `masking`）、依赖清单 diff 的 CVE 检查（有网时拉、断网时用本地快照比对或显式跳过并留痕）。

### 2.3 ③ 合并时：最新主分支上重测（**组合回归缺口**）

**Claude 要点**：合并队列——不直接进 main，先排队，与最新 main 合并后再跑测试，通过才真合入。

**Orcsy 已有**：worktree 隔离、分支合入、合并冲突自愈（0.30.0）、WIP/落地分离。

**缺失**：**合入前没有「与最新 main 合并后重跑一次测试」**。目前冲突才触发自愈，
但「单独测没问题、合了最新才出问题」的组合回归没有被系统性拦截。

**补强建议**：落地「合入前重测」——合入前把任务分支与最新 main 合并（复用冲突自愈的 rebase 机制），
静默重跑受影响测试/构建，通过才落 main。成本可控（只重跑受影响部分），收益是 main 始终可跑。

### 2.4 ④ 合并后：安全到达用户（**发布侧几乎空白**）

**Claude 要点**：功能开关先藏 → latest 尝鲜 → 一周后推 stable → 观察/回滚（关开关最快、重发、回滚兜底）。

**Orcsy 已有**：升级前自动配置备份、手动导入旧包可降级、版本发布走 GitHub/Gitee Release。

**缺失 / 可补强**：
1. **更新通道分级（latest / stable）**：这是当前最大空位——只有单通道 Release。
   → 建议 `latest`（尝鲜）与 `stable`（稳定）两条通道，设置页可切；新版本先进 latest，一周无回滚再推 stable。复用 updater 的 Release 解析。
2. **功能开关（可选，MVP 级）**：对看板新功能/新角色做运行时开关，出问题在设置页/配置一键关（比发新包快）。
   MVP 只做「开关状态入配置 + 看板读取」，不必做远程下发。
3. **观察与回滚**：升级前备份已有；补「记录上一个正常版本」+ 一键回退上一可用版本（配合 stable 通道），
   把回滚从「手动找包」变「一步」。

## 3. 缺口汇总与优先级

| 优先级 | 缺口 | 对应阶段 | Orcsy 现状 | 建议动作 |
| --- | --- | --- | --- | --- |
| **P0** | 风险分级审批 | ② | 人工把关二元 | 按改动对象 0/1/2 人分级，高风险（计费/自更新/egress/配置迁移）强化 |
| **P0** | 合入前重测 | ③ | 冲突才自愈 | 合入前与最新 main 合并后重跑测试，通过才落地 |
| **P0** | 更新通道分级 | ④ | 单通道 Release | latest / stable 双通道，设置页可切 |
| **P1** | AI 审核结构化 | ② | 只有 pass/fail + 返工 | 三分类逐条处置 + 未处理重要问题不通过 + 收口规则 |
| **P1** | 安全门禁默认化 | ② | `security` 可选角色 | 合并前默认密钥扫描 + 依赖 CVE 检查（离线降级留痕） |
| **P1** | CI 门禁 | ② | 靠 Agent 跑测试 | lint/类型/构建/测试独立门禁，证据进 runlog |
| **P1** | 完成证据强化 | ① | 主要看 files_changed | 完成声明附「运行成功 + 截图/日志」证据 |
| **P2** | 功能开关 | ④ | 无 | MVP：开关入配置 + 看板读取 |
| **P2** | 一键回滚上一版本 | ④ | 手动找包 | 记录上一正常版本 + 一步回退 |
| **P2** | Review 空白上下文约束 | ① | 隐式 | 提示词显式剥离写码过程 |

## 4. 结合 Orcsy 定位的取舍（避免照搬）

- Orcsy 是**断网内网 / 桌面 / 国产模型**的无人值守编排器，不是云 SaaS 的 PR 体系。合并队列、canary、
  feature flag 是云服务概念，落到 Orcsy 要改形：
  - 「合并队列」→ 「任务分支合入前与最新 main 合并重测」（单机/私有 git 内实现）；
  - 「canary/latest-stable」→ 「更新通道分级」（Release 两条通道，桌面自更新选择）；
  - 「feature flag」→ 「看板功能开关入配置」（不追求远程下发，先做本地开关 + 快速回退）。
- 安全/CI 门禁要在**离线可用**前提下设计：联网步骤（实时 CVE、远程 CI）做成「有网用、断网降级留痕」，不把离线能力退化掉。

## 5. 建议下一步

1. 把上表 P0 三项（风险分级审批 / 合入前重测 / 更新通道分级）转成各自的设计+实施项，纳入 `docs/roadmap.md` §8 重排优先级（与 1.0 稳定化 S 系不冲突、可与备份/归档集群并行）。
2. P1 四项可作为「质量闭环增强」批次，复用现有 review / security / runlog / local_debug 底座逐项推进。
3. 本评估不落地代码；是否启动由路线图优先级与上述取舍决定。
