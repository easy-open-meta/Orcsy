## 1. 核心设计哲学与团队记忆原则

大模型在处理复杂研发工程时，面临两大天然瓶颈：
1. **上下文窗口与记忆衰退**：对话历史越长，Token 消耗呈几何级数增长，且模型注意力极易被历史排障噪音稀释（灾难性遗忘与幻觉）。
2. **多模型角色异构**：团队中不同 Agent 各司其职且可能绑定不同厂商模型（如 PM 用 Claude 强推理、后端用 DeepSeek-Coder、测试用 GPT-4o），直接传递未整理的原始对话文本（Messages History）在技术上不可行且极不经济。

因此，Orcsy 坚守 **「结构化产出物与精准透传（Artifact-based Handoff）」** 的团队记忆演进哲学：
> **不直接共享原始聊天轮次，而是将记忆沉淀为高层次结构化知识、文件产出与上下文摘要，在正确的时机精准喂给对应的角色。**

## 2. 核心演进方向一：项目小组协同与长期团队记忆增强

### 2.1 项目架构黑板报与动态演进记忆（`ARCHITECTURE.md` / `SCRATCHPAD.md`）

- **现状痛点**：目前后置任务通过 `depends_on` 只能拿到直接前置任务的交付摘要；面对几十个任务组成的超大项目时，缺乏全局系统架构蓝图，开发容易盲人摸象。
- **演进方案**：
  1. **架构黑板报机制**：在项目根目录（或 `tasks/.architecture.md`）维护一份轻量、高密度的全局系统架构备忘录；
  2. **角色协同维护**：
     - **项目经理 PM**：在首次拆解系统需求时梳理核心架构分层、模块边界、关键技术选型与公共数据模型；
     - **前后端开发**：在完成重大核心接口或数据表变更后，按轻量协议在黑板报追加新增的关键路由与文件导引（限制 200 字以内增量）；
  3. **只读低成本消费**：所有角色的任务启动时，系统自动抽取黑板报前 2000~4000 字符注入系统提示词作为全局参照，以极低 Token 成本维持小队成员对项目全貌的共识。

> **实现状态（2026-11-17，Phase 1）**：已落地 `orcsy/prompts.py` 注入（前 3000 字符）、
> `update_architecture` 专用工具（只写 `ARCHITECTURE.md`，PM replace / 开发 append，
> **正文要求英文以节省 token**）、PM/开发角色维护协议与设置页「项目架构记忆」工具分类。设计见
> [`docs/design-team-memory-phase1.md`](design-team-memory-phase1.md)。

### 2.2 需求批次临时共享剪贴板（Team Session State / Ephemeral Bus）

- **现状痛点**：在「后端开发 → 前端对接 → QA 联调」流水线推进时，某些运行时生成的临时状态（如本地微服务临时启动端口、测试账号动态生成的 JWT Token、临时测试数据库 DSN）无法方便地向下游传递。
- **演进方案**：
  1. **批次临时状态总线**：在同一调度轮次或同属于一个父需求（`parent_id`）的协作会话内，提供轻量键值剪贴板；
  2. **工具扩展**：开发角色可调用 `session_share(key, value)` 暂存非代码运行态信息，QA 在联调测试时可调用 `session_read(key)` 直接读取测试凭证或端口，免去繁琐的日志正则捕获；
  3. **生命周期回收**：需求验收归档（或人工终止）时，临时剪贴板立即被物理销毁，敏感凭据不在任务文件中长期留痕，兼顾效率与安全。

> **实现状态（2026-11-17，Phase 1）**：已落地 `orcsy/session_bus.py` +
> `session_share` / `session_read` 工具；批次沿 `parent_id` 追到根需求，状态存
> `<配置目录>/state/session_bus/`，批次全部终态后物理删除，7 天 TTL 兜底。
> 设计见 [`docs/design-team-memory-phase1.md`](design-team-memory-phase1.md)。

### 2.3 历史已完成任务智能召回（Task Memory & Vector RAG）

- **现状痛点**：随着项目推进，`tasks/done/` 归档了数以百计的已完成任务。新任务下发时，Agent 无法从相似历史任务中吸取已有的解决方案。
- **演进方案**：
  1. **本地任务嵌入索引**：在数据目录维护轻量向量索引或 BM25 检索库，任务归档时将 `title + description + 审查意见 + 变更文件` 向量化；
  2. **先验经验推荐**：新任务下发时，系统自动搜索最相似的 2~3 个历史已解决任务，提取其解决思路与修改过的核心文件路径，注入到任务提示词的「📚 相似历史任务参考」节中；
  3. **降低探索轮数**：开发 Agent 一上手即可直奔相关历史代码位置，大幅压缩探索阶段的 `list_dir` / `grep` 轮次。

### 2.4 任务内动态只读子代理并发探索（Task Subagents / Fan-Out Delegation）

- **现状痛点**：单任务执行内部采用严格串行对话循环（大模型思考 15s → 调单一工具 → 等结果回写 → 再思考），在面临中大型工程摸底（如 PM 探索 20+ 轮）时耗时累积达到 4~5 分钟，且主上下文被大量文件片段噪音稀释。
- **演进方案**（详见 `docs/design-task-subagents.md`）：
  1. **探索委托工具**：为主 Agent 提供 `delegate_explore` 工具，支持单次并发派生 2~4 个轻量只读子代理；
  2. **轻量并发摸底**：各子代理在独立轻量线程中并行探索各自目录/关注点，完成 2~4 轮后向主 Agent 汇报高度提炼的结构化 Markdown 调研报告；
  3. **耗时极致压缩**：以“单轮并发”取代“数十轮串行”，探索阶段耗时由 4 分钟压缩至 30~45 秒（提速 4~6 倍），主上下文保持极度纯净。

## 3. 核心演进方向二：研发小队角色丰富与编排智能化

### 3.1 扩展专业职能角色

在当前 `pm`、`backend`、`frontend`、`qa` 4 大核心角色基础上，进一步扩充标准职能预设库：
1. **运维与 DevOps 工程师（`devops`）**：
   - 负责 Dockerfile、docker-compose、CI/CD 脚本、K8s 声明与环境配置编写维护。
2. **UI / 视觉审查专家（`ui_critic`）**：
   - 利用本地 Chromium 浏览器截图工具，对照设计规范或视觉指引对前端页面排版、间距与响应式缩放做纯视觉审美与体验把关。
3. **安全合规审计工程师（`security`）**：
   - 在代码合并前执行静态代码扫描与依赖组件 CVE 检索，识别 SQL 注入、越权与硬编码密钥风险。

### 3.2 可视化 DAG 依赖编排与流水线看板

- **交互演进**：在 Web 看板提供类似有向无环图（DAG）的节点连线编辑器；
- **直观拓扑展示**：直观展示需求从 PM 拆解、前后端分叉并行、合并到 QA 验收的全链路节点，节点实时显示「等待中 / 执行中 / 回归中 / 已完成」状态及对应模型耗时，支持拖拽连线调整依赖关系。

### 3.3 合并冲突自动变基与自愈（Auto-Rebase & Conflict Self-Healing）

- **现状痛点**：多任务并行并在 worktree 合入主分支时，若触碰同个公共文件（如路由注册表或 `package.json`），可能会引发 Git 合并冲突，目前需打回返工或等人工介入。
- **演进方案**：
  - 合并冲突发生时，系统不直接报错，而是为该开发角色自动构建一个「冲突消解专用任务」；
  - 提示词注入冲突文件标记（`<<<<<<<` / `=======` / `>>>>>>>`），由开发 Agent 结合前后端意图自动解决冲突并跑单元测试，验证通过后自动完成提交，进一步降低人工介入频率。

### 3.4 可插拔外部编码执行器（Generic Harness，评估稿）

- **现状痛点**：内置 `builtin` 编码循环绑定自有 LLM 协议与内置工具沙箱，无法直接复用外部已成熟的编码执行器（Claude Code、Codex CLI 等）在 Git worktree 内完成「探索 → 编码 → 测试」，也无法让受限国产模型与顶级 CLI 编码能力互补。
- **演进方案**（详见 [`docs/design-generic-harness.md`](design-generic-harness.md)）：
  1. **权责分离**：Orcsy 继续负责任务调度、隔离、验收与落地；外部 Harness 只负责发现与编码，仅交付「工作目录改动 + 执行结果」；
  2. **可选旁路**：`runner: builtin | external` 逐项目/逐成员选择，默认 `builtin` 不变；无 Git、嵌套 Git 等无可靠单 worktree 隔离的场景首期拒绝外部运行；
  3. **结果真值**：退出码 0 ≠ 任务完成；`completed` 需结构化成功结论 + Orcsy 自行计算的可提交改动；硬预算、隔离、审查独立性无法保障时 fail closed 拒跑。

> **状态（2026-11-23 重估）**：评估稿，**尚未实施**；列为 P1 可选差异化能力，M0 安全基线先行，实施与 S 系配置/审查链路有交叉，须协调合并，不默认阻塞 1.0.0。四项产品决策已全部确认：**部署信任等级 = 首期只跑本机可信 CLI（A 档，OS/容器强隔离与远程 Harness 单列 P3）**；**预算/审查 = 不可计量/不可确认即 fail closed，关闭须显式配置表达**；**通用范围 = 白名单具名 adapter、不承诺零配置**；**首个验收 CLI = 假 CLI → Claude Code → Codex**。实施按 **M0（契约 + fail-closed 安全基线）→ M1（后端旁路）→ M2（配置与产品入口）→ M3（真实 CLI 逐名接入）** 推进，粗估 M0–M2 约 2–3 周、首个真实 CLI 另 1–2 周。

## 4. 核心演进方向三：质量闭环与测试资产沉淀

### 4.1 测试用例资产化（Automated Test Asset Accumulation）

- **测试工程师深化**：QA 不仅负责一次性黑盒联调验证，还鼓励在开启 `allow_test_scripts` 时，自动把手动发现的 Bug 复现步骤转化为持久化的端到端自动化测试脚本（如 Playwright / pytest / vitest 用例）；
- **回归测试集常态化**：项目后续任务每次执行 Review 审查或回归联调时，自动重跑这些历史沉淀的测试用例，防止系统在快速迭代中产生代码退化。

### 4.2 运行态日志与异常自动捕获转任务（Sentry / Log Watcher 集成）

- 监控开发服务（`dev_server`）或外部测试环境的运行时异常；
- 监听到未捕获异常或 5xx 告警时，自动组装堆栈并生成带 `[Bug]` 标签的 Markdown 任务注入项目任务队列，由小队自动排查修复。

## 6 V1 可信流水线（已交付）

### 6.1 定位修正

方向从「可信单实例」收窄为：

> **能在断网内网、Windows 工作站上用国产模型跑完「拆单 → 开发 → 联调 → 审查 → 提交」的无人值守研发流水线，代码与密钥不出网。**

「可信」（留痕、幂等、预算、熔断）是支撑该定位的**工程底座**，不作为单独卖点：同类项目已把原子锁、预算硬闸、审批门、审计日志做成免费基线，Orcsy 的差异化在**离线零依赖、桌面形态、国产模型与镜像生态、出站脱敏、CDP 浏览器联调**。

### 6.2 改造项与顺序

顺序不可打乱：R1 是其余三项的证据基础。

| 编号 | 改造项 | 关键交付 | 里程碑 |
| --- | --- | --- | --- |
| R1 | 运行台账与回放 | 统一 `run_id`；`meta.json / events.jsonl / diff.patch / test.log / review.json / usage.json`；看板回放 | M1 |
| R2 | 幂等与断点续跑 | 任务指纹、带 TTL 心跳的租约、续跑决策表、提交前二次校验 | M2 |
| R3 | 预算硬闸 | token/成本上限；软停（项目日窗）+ 硬停（单任务）；`blocked + block_reason` | M3 |
| R4 | 熔断停机 | 连续失败/窗口失败率；项目级暂停、可解释横幅、人工恢复 | M4 |
| R5 | 写操作审计 | `logs/audit.jsonl`；登录、任务、设置、提交、API Key 全留痕 | M5 |

| P2 | 只读聚合契约 | `GET /api/state/export`，不实现跨实例协调 | 预留 |

### 6.3 与现有能力的边界（不重造）

- **已有、只接入**：审查门（不通过不合并、返工上限）、任务 DAG、worktree 生命周期、脱敏、用量台账、登录/会话/失败锁定、启动恢复。
- **明确不改**：任务状态域（`open/in_progress/done/blocked/cancelled`）、`depends_on` 语义、端口与四种部署方式、Apache-2.0。
- **明确不做**：多实例/集群、SSO/RBAC、替换内核为 harness adapter（改为 `runner: external` 旁路）、自动回滚（保留 WIP 更可审计）。

## 7. 1.0 稳定化路线图（S1~S5）：1.0.0 的门槛工程

> 背景：V1 底座与 Phase 1 已交付，功能面已齐。**1.0.0 的语义是「向后兼容契约
> 生效」而非质量奖**——minor 升级保证配置/数据/API 向后兼容，补丁可安全替换
> 生产环境。门槛本质是「敢承诺不弄坏用户的配置与数据」，S1~S5 即为此而设
> （S=Stability，编号刻意避开 V1 已用的 M0~M6）。

| 编号 | 改造项 | 关键交付 | 退出标准 |
| --- | --- | --- | --- |
| S1 | 配置与数据格式版本化 | `config_version` 与显式迁移器已交付；现有 0.24/0.26 文件是构造回归夹具，含后续新增分区，不等同历史原始导出；直接设置服务往返已补测试 | 真实旧版配置与 HTTP 看板完整往返仍待补证，尤其可信 0.25 样本；不能以构造夹具和服务直调用替代端到端验收 |
| S2 | 升级演练 + 配置备份/恢复 | 升级前自动备份及 local/WebDAV/S3 目标已交付（0.28.0/0.33.0）；隔离目录模拟迁移/故障/恢复已覆盖，非真实 N-1 二进制升级 | N-1 → N 数据目录交接、失败恢复演练和 smoke 回归通过；完整安装/降级实测仍待补证，云目标扩展不作为 1.0 门槛 |

### S4 生产观察记录（未开始，不能视为已完成）

S4 的退出标准要求正式生产实例连续观察 4–8 周。当前仓库仅记录观察方法和证据格式；没有把开发机验证、CI smoke、发布准备或短期试跑计入 S4 观察期。

**观察前置条件**

- [ ] 指定一个正式运行实例、负责人、开始日期和计划结束日期（4–8 周）。
- [ ] 固定运行版本、配置快照标识、项目范围和数据目录备份位置。
- [ ] 确认运行台账、审计日志、任务状态变更和提交记录可导出且可追溯。
- [ ] 建立每日或每个任务周期的观察记录，不采集 API Key、密码或任务正文中的敏感值。
- [ ] 明确缺陷升级联系人、暂停条件和恢复步骤。

**每次观察记录**

| 字段 | 记录内容 |
| --- | --- |
| 时间窗口 | UTC 起止时间、运行版本、实例标识 |
| 任务统计 | 新建、完成、受阻、取消、重试数量 |
| 数据完整性 | 配置、任务、运行台账、审计日志是否可读；备份是否可恢复抽查 |
| 升级结果 | 是否发生升级；是否需要人工重配；使用的包与 SHA256 |
| 提交与预算 | 是否有重复提交、重复执行、预算越界或异常熔断 |
| 缺陷与处置 | 事件编号、影响、证据链接、修复版本、回归结果 |

**S4 退出证据包**

- [ ] 连续 4–8 周的原始观察记录和汇总表。
- [ ] 零数据丢失的核对结果，包含抽样范围和备份恢复证据。
- [ ] 零升级后人工修配置的记录；如有例外，必须解释并判定退出失败或延长观察。
- [ ] 零重复提交、零预算越界的运行台账查询结果。
- [ ] 生产缺陷及修复的完整闭环；未关闭的 blocker 不得退出。
- [ ] 负责人签字或等价审批记录，以及最终版本和配置快照索引。

**当前证据备注（2026-11-24）**：CI 构建、SHA256 校验和 prepublish smoke（打包 CLI 安装依赖可能联网）只能作为发布工程证据，不能替代生产观察。S4 尚未开始，未形成连续观察数据，也未达到退出标准。

### S5 发布工程证据（待验）

- [ ] CI 构建生成七个预期附件及各自 `.sha256`，逐一校验文件名、大小和摘要；下载后再次校验且不含多余附件。

### 8.1 执行顺序与交叉约束

1. **先保发布完整性**：S1–S3 核验、未签名附件摘要校验与恢复演练；S5 签名
   暂缓且仍未退出。在金丝雀前定好阶段④
   通道及候选晋级政策，latest/stable 实现可独立排期，不凭评估稿强行纳入 1.0。
2. **再补合入质量**：阶段③合入前重测先试点；阶段②机器门禁、结构化审核和
   风险提示接现有审查/人工提交，不默许从“人工把关”直接跳成“低风险自动合并”。
3. **Harness 单独推进契约验证**：M0→M1 假 CLI→M2 配置/UI→M3 Claude Code
   首验，Codex 后置；它会触及 config、executor、claims、review、RunLog 与看板，
   与质量门禁共享修改面，采用接口先定、分支串行集成，而不是声称互不相交。
4. **发布基础就绪后再开 UI OTA 通道**：不必等待 Harness 完工，但须先在完整 release 上确定可信发布/回退和前后端
   兼容规则，再补磁盘覆盖→清单校验→确认应用→SW/e2e；UI OTA 默认关闭，
   不用于掩盖需后端修复的缺陷。开始 S4 正式金丝雀后不再混入未验收新能力。

**待定产品政策**：阶段②“低风险 0 人/高风险 2 人”是否真的改变提交权限；
阶段④ latest/stable 如何标记、谁批准晋级与默认通道；UI OTA 选清单还是 tag、
确认还是自动、是否提供重置命令/按钮。未决项只安排设计/试点，不写作已确认承诺。
Phase 3 完整 RAG 与资产沉淀排在 1.0 后；1.0 按 §7 出口标准判定，不按日历。
