# Orcsy 未来开发路线图（Development Roadmap）

> 状态：**规划与演进蓝图**
> 初始制定版本：**v0.21.0**
> 核心演进主线：**从「单兵执行」到「多角色项目小队协同」，再到「具备自愈、长期团队记忆与智能演进的工业级无人研发组织」**。

---

## 1. 核心设计哲学与团队记忆原则

大模型在处理复杂研发工程时，面临两大天然瓶颈：
1. **上下文窗口与记忆衰退**：对话历史越长，Token 消耗呈几何级数增长，且模型注意力极易被历史排障噪音稀释（灾难性遗忘与幻觉）。
2. **多模型角色异构**：团队中不同 Agent 各司其职且可能绑定不同厂商模型（如 PM 用 Claude 强推理、后端用 DeepSeek-Coder、测试用 GPT-4o），直接传递未整理的原始对话文本（Messages History）在技术上不可行且极不经济。

因此，Orcsy 坚守 **「结构化产出物与精准透传（Artifact-based Handoff）」** 的团队记忆演进哲学：
> **不直接共享原始聊天轮次，而是将记忆沉淀为高层次结构化知识、文件产出与上下文摘要，在正确的时机精准喂给对应的角色。**

## 2. 核心演进方向一：项目小组协同与长期团队记忆增强

### 2.1 项目架构黑板报与动态演进记忆（`ARCHITECTURE.md` / `SCRATCHPAD.md`）

- **现状痛点**：目前后置任务通过 `depends_on` 只能拿到直接前置任务的交付摘要；面对几十个任务组成的超大项目时，缺乏全局系统架构蓝图，开发容易盲人摸象。
- **演进方案**：
  1. **架构黑板报机制**：在项目根目录（或 `tasks/.architecture.md`）维护一份轻量、高密度的全局系统架构备忘录；
  2. **角色协同维护**：
     - **项目经理 PM**：在首次拆解系统需求时梳理核心架构分层、模块边界、关键技术选型与公共数据模型；
     - **前后端开发**：在完成重大核心接口或数据表变更后，按轻量协议在黑板报追加新增的关键路由与文件导引（限制 200 字以内增量）；
  3. **只读低成本消费**：所有角色的任务启动时，系统自动抽取黑板报前 2000~4000 字符注入系统提示词作为全局参照，以极低 Token 成本维持小队成员对项目全貌的共识。

### 2.2 需求批次临时共享剪贴板（Team Session State / Ephemeral Bus）

- **现状痛点**：在「后端开发 → 前端对接 → QA 联调」流水线推进时，某些运行时生成的临时状态（如本地微服务临时启动端口、测试账号动态生成的 JWT Token、临时测试数据库 DSN）无法方便地向下游传递。
- **演进方案**：
  1. **批次临时状态总线**：在同一调度轮次或同属于一个父需求（`parent_id`）的协作会话内，提供轻量键值剪贴板；
  2. **工具扩展**：开发角色可调用 `session_share(key, value)` 暂存非代码运行态信息，QA 在联调测试时可调用 `session_read(key)` 直接读取测试凭证或端口，免去繁琐的日志正则捕获；
  3. **生命周期回收**：需求验收归档（或人工终止）时，临时剪贴板立即被物理销毁，敏感凭据不在任务文件中长期留痕，兼顾效率与安全。

### 2.3 历史已完成任务智能召回（Task Memory & Vector RAG）

- **现状痛点**：随着项目推进，`tasks/done/` 归档了数以百计的已完成任务。新任务下发时，Agent 无法从相似历史任务中吸取已有的解决方案。
- **演进方案**：
  1. **本地任务嵌入索引**：在数据目录维护轻量向量索引或 BM25 检索库，任务归档时将 `title + description + 审查意见 + 变更文件` 向量化；
  2. **先验经验推荐**：新任务下发时，系统自动搜索最相似的 2~3 个历史已解决任务，提取其解决思路与修改过的核心文件路径，注入到任务提示词的「📚 相似历史任务参考」节中；
  3. **降低探索轮数**：开发 Agent 一上手即可直奔相关历史代码位置，大幅压缩探索阶段的 `list_dir` / `grep` 轮次。

## 3. 核心演进方向二：研发小队角色丰富与编排智能化

### 3.1 扩展专业职能角色

在当前 `pm`、`backend`、`frontend`、`qa` 4 大核心角色基础上，进一步扩充标准职能预设库：
1. **运维与 DevOps 工程师（`devops`）**：
   - 负责 Dockerfile、docker-compose、CI/CD 脚本、K8s 声明与环境配置编写维护。
2. **UI / 视觉审查专家（`ui_critic`）**：
   - 利用本地 Chromium 浏览器截图工具，对照设计规范或视觉指引对前端页面排版、间距与响应式缩放做纯视觉审美与体验把关。
3. **安全合规审计工程师（`security`）**：
   - 在代码合并前执行静态代码扫描与依赖组件 CVE 检索，识别 SQL 注入、越权与硬编码密钥风险。

### 3.2 可视化 DAG 依赖编排与流水线看板

- **交互演进**：在 Web 看板提供类似有向无环图（DAG）的节点连线编辑器；
- **直观拓扑展示**：直观展示需求从 PM 拆解、前后端分叉并行、合并到 QA 验收的全链路节点，节点实时显示「等待中 / 执行中 / 回归中 / 已完成」状态及对应模型耗时，支持拖拽连线调整依赖关系。

### 3.3 合并冲突自动变基与自愈（Auto-Rebase & Conflict Self-Healing）

- **现状痛点**：多任务并行并在 worktree 合入主分支时，若触碰同个公共文件（如路由注册表或 `package.json`），可能会引发 Git 合并冲突，目前需打回返工或等人工介入。
- **演进方案**：
  - 合并冲突发生时，系统不直接报错，而是为该开发角色自动构建一个「冲突消解专用任务」；
  - 提示词注入冲突文件标记（`<<<<<<<` / `=======` / `>>>>>>>`），由开发 Agent 结合前后端意图自动解决冲突并跑单元测试，验证通过后自动完成提交，进一步降低人工介入频率。

## 4. 核心演进方向三：质量闭环与测试资产沉淀

### 4.1 测试用例资产化（Automated Test Asset Accumulation）

- **测试工程师深化**：QA 不仅负责一次性黑盒联调验证，还鼓励在开启 `allow_test_scripts` 时，自动把手动发现的 Bug 复现步骤转化为持久化的端到端自动化测试脚本（如 Playwright / pytest / vitest 用例）；
- **回归测试集常态化**：项目后续任务每次执行 Review 审查或回归联调时，自动重跑这些历史沉淀的测试用例，防止系统在快速迭代中产生代码退化。

### 4.2 运行态日志与异常自动捕获转任务（Sentry / Log Watcher 集成）

- 监控开发服务（`dev_server`）或外部测试环境的运行时异常；
- 监听到未捕获异常或 5xx 告警时，自动组装堆栈并生成带 `[Bug]` 标签的 Markdown 任务注入项目任务队列，由小队自动排查修复。
