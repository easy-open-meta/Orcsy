1. 先看这里：5 分钟跑通第一个任务

如果你已经装好 Orcsy，只想马上试一次，按下面五步走：

  1. 打开看板：双击桌面上的 Orcsy 图标（开始菜单里也叫 Orcsy），或访问 http://127.0.0.1:5116。
  2. 填模型：点顶部「项目与设置」→ 在「🤖 大模型接入」卡片里填 API Key、API 地址、模型名 → 点「测试连接」→ 成功后点「保存模型配置」。
  3. 加项目：点右上角「＋ 新建项目」→ 选一个你电脑上的项目文件夹 → 点「保存」。Orcsy 会自动在该文件夹里建 tasks/ 和 AGENT.md，不会动你原来的代码。
  4. 加任务：回到「看板」页，在项目卡片里输入一句任务标题（例如「修复登录页在 125% 缩放下错位」），选优先级，点「添加」。
  5. 让它开工：点顶部「▶ 立即扫描」。任务状态会从「待办」变成「执行中」，跑完后变成「已完成」或「受阻」。完成后项目里会多出一条 Git 提交（如果项目是 Git 仓库）。

💡 第一次使用建议先拿一个测试项目或副本练手。Orcsy 会真实修改文件、真实执行命令。如果项目是 Git 仓库，改动会先在临时工作副本里完成，成功后再合并回项目；非 Git 项目则直接在项目目录里修改。

2. Orcsy 是什么，能帮你做什么

2.1 一句话说明

Orcsy 是一个「把任务写下来，就自动帮你做」的工具。 你用一个 Markdown 文件描述要做什么，Orcsy 会定时检查任务清单，把任务交给 AI 助手，让它在你的项目里读代码、改文件、跑测试；完成后先由另一个模型独立审查，改动落到工作区等你确认提交——每一步都留有运行台账，随时可回放追溯。

可以把它想象成：

  • 你是「产品经理」，负责写清楚要做什么、做到什么程度算完成；
  • Orcsy 是「项目经理 + 安全员」，负责排优先级、安排谁来做、盯着进度，并在关键节点把关；
  • 大模型（AI）是「执行工程师」，负责真正动手改代码；
  • 独立审查 Agent 是「验收员」，用另一个模型复核成果，防止「自己审自己」；
  • 看板是「办公室大屏」，随时能看到谁在做什么、做到哪一步。

2.2 它适合做什么

  • 有明确验收标准的开发任务：修 Bug、加小功能、补测试、改文案、重构一小块代码；
  • 需要重复执行的维护工作：依赖升级后跑测试、批量修改配置、生成文档；
  • 把 GitHub / Gitee / GitLab / Gitea 上的 Issue 自动变成开发任务；
  • 多个项目排队执行，或者多个项目并行执行；
  • 晚上或周末无人值守地推进任务。

2.3 它不适合做什么

  • 需求本身很模糊，连你自己都说不清「做成什么样算完成」；
  • 需要大量产品决策、UI 审美判断、数据库结构大改的任务；
  • 需要访问生产数据库、第三方后台、密钥管理系统，但你没有把权限交给它；
  • 需要「一键上线」「自动发布到应用商店」这类高风险操作（Orcsy 不负责部署上线，只负责改代码和提交）。

2.4 使用它需要会编程吗

不需要你会写代码，但需要你能做到下面几件事：

  • 会安装 Windows 软件、会解压文件；
  • 会申请一个大模型 API Key（各家平台的网页操作）；
  • 能用一两句话把任务说清楚，最好写上「验收标准」；
  • 知道自己的项目文件夹在哪里；
  • 出问题时愿意看一眼「运行日志」里的中文提示。

如果你完全不想碰命令行，优先使用 Windows 安装包，其余步骤都在浏览器里点鼠标完成。

3. 三个核心概念，用大白话解释

3.1 项目（Project）

一个「项目」就是你的一个代码文件夹，例如 D:\Repos\my-app。

Orcsy 只在这个文件夹里做两件事：

  1. 创建（如果还没有）tasks/ 文件夹，用来放任务；
  2. 创建（如果还没有）AGENT.md 文件，用来告诉 AI「这个项目有什么规矩」。

它不会动你项目里的其它文件结构，也不会把配置、日志、技能写进项目目录。

3.2 任务（Task）

一个任务就是一个 Markdown 文件（.md），放在项目的 tasks/ 目录里。

文件名就是任务 ID，例如 P1-修复登录页崩溃.md。文件开头有一段「元信息」（标题、优先级、状态），下面是你写的需求、现象、验收标准。

你可以：

  • 在看板上点鼠标创建任务；
  • 直接往 tasks/ 文件夹里拖一个 .md 文件；
  • 用文本编辑器打开任务文件修改。

三种方式效果一样，因为看板改的就是这些文件。

3.3 Agent（AI 助手）

每个项目有自己专属的 Agent。它不是一个常驻的机器人，而是「每次领到一个任务，就临时开工」的执行者。

它工作时会：

  1. 读项目的 AGENT.md，了解技术栈、运行命令、代码规范；
  2. 读任务文件，理解要做什么；
  3. 如果项目是 Git 仓库，在项目里创建一个临时工作副本（git worktree），所有修改都先发生在这里；非 Git 项目则直接在项目目录里修改；
  4. 读文件、改文件、跑测试、跑构建；
  5. 完成后报告结果，由 Orcsy 统一提交、合并回主分支；
  6. 把结果写回任务文件，并把完成的任务归档到 tasks/done/。

💡 为什么要用临时副本？因为 AI 也会犯错。Git 项目里所有改动先在副本里做，确认没问题再合并；如果任务受阻，副本会被丢弃，你的主工作区不会被弄脏。非 Git 项目没有这层保护，首次使用更建议先备份或在副本上练习。

4. 安装部署：选一种适合你的方式

4.1 先选方式

你的情况 推荐方式 难度 需要什么
Windows 个人电脑，想最省事 Windows 安装包 ★☆☆ 一个 API Key
想查看/修改源码，或参与开发 源码运行 ★★★ 会一点命令行，装 uv
服务器、NAS，不想装运行环境 Docker Compose ★★☆ 会 Docker 基本操作
Linux 服务器，想开机常驻 Linux systemd ★★★ root 权限，会一点 Linux

对绝大多数普通用户，选 Windows 安装包就够了。

4.2 方式一：Windows 安装包（推荐）

准备工作

  • Windows 10 / 11；
  • 一个大模型 API Key（例如 DeepSeek、智谱 GLM、Kimi、OpenAI、通义千问等）；
  • 一个你想交给 Orcsy 的项目文件夹；
  • 建议项目是 Git 仓库（不是也能用，只是不会自动提交/合并）。

安装步骤

  1. 打开项目发布页，下载 orcsy-setup-0.35.0-windows-amd64.exe（ARM64 机器可优先用原生 orcsy-setup-0.35.0-windows-arm64.exe；amd64 包也能在 ARM64 Win11 上通过仿真运行）。
    • Gitee：https://gitee.com/java-and-net/Orcsy/releases
    • GitHub：https://github.com/easy-open-meta/Orcsy/releases
  2. 双击安装包。如果 Windows 弹出「已保护你的电脑」，点「更多信息」→「仍要运行」。
  3. 按向导点「下一步」。安装位置可以保持默认 C:\Program Files\Orcsy，也可以改到一个你有写权限的目录（例如 D:\Tools\Orcsy）。
    • 装在 C:\Program Files 下：以后自动更新时会弹一次管理员授权（UAC），点「是」即可；
    • 装在用户可写目录：以后更新全程无弹窗，更省心。
  4. 附加任务里可以勾选「初始化示例任务」。它只会在数据目录放一份任务模板，方便你参考，不勾也不影响使用。
  5. 点「安装」，完成后程序会自动启动：
    • 右下角任务栏出现 Orcsy 托盘图标；
    • 浏览器自动打开看板 http://127.0.0.1:5116。
  6. 如果浏览器没有自动打开：右键托盘图标 →「显示主界面」，或手动访问上面的地址。

安装后你要知道的三件事

  • 数据目录：C:\Users\<你的用户名>\AppData\Roaming\Orcsy
    • config.yaml：配置文件（含 API Key，不要发给别人）；
    • skills\：技能库；
    • logs\：运行日志；
    • logs\usage.jsonl：用量记录。
  • 程序目录：只放程序本体，不放你的数据。
  • 卸载：Windows「设置 → 应用 → 已安装的应用」里找到 Orcsy 卸载；卸载时可以选择是否一并删除数据目录。

⚠️ 第一次启动会自动生成 config.yaml，你不需要手动创建。模型密钥推荐在看板里填，保存后立即生效。

4.3 方式二：源码运行（适合想看源码的人）

前提：电脑上已安装 uv（一个 Python 环境管理工具）。没有 Python 也没关系，uv 会自动准备 Python 3.11+。

# 1. 下载源码
git clone https://gitee.com/java-and-net/Orcsy.git orcsy
cd orcsy

# 2. 安装依赖
uv sync

# 3. 生成配置和模板到 run/ 目录
uv run orcsy init --dir run

# 4. 编辑 run/config.yaml：至少填 api_key、base_url、model
#    然后把 projects 指向你的项目（用绝对路径）

# 5. 检查配置和任务格式
uv run orcsy validate --config run/config.yaml

# 6. 启动看板（同时启动定时调度，并自动打开浏览器）
uv run orcsy web --config run/config.yaml

常用启动参数：

参数 作用
--port 8080 换一个看板端口
--host 0.0.0.0 允许局域网访问（必须同时设置登录密码）
--no-browser 启动时不自动打开浏览器
--no-tray 不显示系统托盘图标
--no-sched 不启动定时调度，只保留手动「立即扫描」

只想当命令行调度器、不要看板：

uv run orcsy run --config run/config.yaml          # 持续调度
uv run orcsy run --config run/config.yaml --once   # 只跑一轮就退出（适合计划任务/cron）

4.4 方式三：Docker 部署（服务器 / NAS）

前提：服务器已安装 Docker 和 Docker Compose。

# 1. 在项目根目录构建并启动
docker compose up -d --build

# 2. 第一次启动会生成 ./orcsy-data/config.yaml
#    因为容器对外监听 0.0.0.0，必须设置登录密码，否则会拒绝启动
#    编辑 ./orcsy-data/config.yaml，把 web.auth_password 改成强密码
docker compose restart

# 3. 浏览器打开
#    http://<服务器IP>:5116

目录对应关系：

宿主机 容器内 放什么
./orcsy-data /data 配置、技能库、日志、用量记录
./projects /projects 受管项目（建议每个项目一个子目录）

重要规则：

  • 看板里新建项目时，项目路径要填容器内路径，例如 /projects/my-app，对应宿主机的 ./projects/my-app；
  • 宿主机上的 ./projects/my-app 需要是 Git 仓库；
  • 如果要让 Orcsy 能推送到远程仓库，需要配置 Git 凭据：
    • HTTPS：把 token 写进远端地址；
    • SSH：按 docker-compose.yml 里的注释挂载 ~/.ssh。
  • 查看日志：docker compose logs -f；
  • 停止：docker compose down；
  • 升级：备份 ./orcsy-data，拉取新源码后重新 docker compose up -d --build。

4.4.1 给 Agent 补齐测试与构建工具（卷挂载 / env.vars）

Agent 执行测试、构建命令用的工具都在容器里找。缺什么有三种补法：

(1) 卷挂载（适合自包含工具）——编辑 docker-compose.yml 的 volumes，把宿主机的工具目录挂进容器：

volumes:
  - ./orcsy-data:/data
  - ./projects:/projects
  - ./team-tools:/usr/local/bin/team-tools   # 自定义工具目录
  • 执行命令时 PATH 会自动追加 /usr/local/bin、/usr/local/go/bin、/opt/homebrew/bin 等常见目录——把可执行文件放（或软链）到 /usr/local/bin 下，Agent 直接裸名调用；
  • 挂到其他位置也可以，Agent 用绝对路径调用（它能浏览容器文件系统）；
  • 适合自包含二进制：Node.js、Go 工具链、JDK、打包好的单文件测试器。

(2) env.vars 环境变量注入——config.yaml 的 env.vars（或「设置 → 环境变量」）里配的任意键值对会注入 Agent 的全部子进程（执行命令、跑测试、构建、子代理），且优先于默认值：

env:
  vars:
    JAVA_HOME: /opt/jdk
    PATH: /opt/team-tools:/usr/local/bin:/usr/local/go/bin:/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin

注意 PATH 是整体替换（不展开 $PATH），写全即可；看板保存即热生效。

(3) 让 Agent 自己装（env-setup 技能）——什么都不配，Agent 发现缺工具时会按任务自动安装：预检诊断 → 镜像源测速选源 → 安装 → PATH 修复 → 验证后继续。对主流模型很可靠。

边界提醒：卷挂载适合自包含二进制；pytest 这类 Python 包工具不能用宿主机挂载——容器内外解释器与 site-packages 不匹配，挂了也 import 不了。Python 工具按优先级：扩展镜像（FROM orcsy:latest 后 RUN pip install pytest ...，团队标准化最干净）→ 交给 env-setup 现场装 → 在容器里手动装一次（docker exec -it orcsy sh -c "python -m ensurepip -q; pip install -q pytest"，容器 venv 默认无 pip 需先引导；重建容器后需重装）。

6. 接入你的第一个项目

6.1 新建项目

点右上角「＋ 新建项目」（或设置页「📁 受管项目」里的同名按钮）。

新建或编辑项目时，进阶设置会分组并预设收起，需要时可展开；收起分组不会启用或停用其中的功能。手机上则采用单栏版面，操作按钮固定在底部。桌面和手机页面均可点击左上角的 Orcsy Logo 快速返回看板首页。

按顺序填写：

  1. 项目名：建议用字母、数字、连字符（也允许下划线），例如 my-app；不要有空格和特殊符号，且不能以符号开头。它会出现在日志和分支名里。
  2. 每轮最多任务数：默认 1。意思是「每一轮扫描，这个项目最多做几个任务」。刚开始建议保持 1，稳定后再加。
  3. 项目路径：点「选择…」选你的项目文件夹，或直接粘贴绝对路径，例如 D:\Repos\my-app。
  4. 任务目录：默认 tasks，保持默认即可。
  5. 指引文件：默认 AGENT.md，保持默认即可。
  6. 工具循环轮数上限：默认 40。AI 做任务时最多「思考—操作」多少轮；填 -1 表示不限制（不建议新手使用）。
  7. 工作分支：可选。留空表示在项目当前分支上工作。
  8. 命令白名单：可选。留空使用默认白名单（python、node、npm、git、dotnet 等常见命令）。
  9. 绑定专属模型：可选。打开后可以给这个项目单独指定模型；不填的字段自动继承全局配置。
  10. 访问权限：默认「跟随全局」。想更安全可以选「变更前询问」。
  11. 覆盖 Agent 工具开关：可选。默认跟随全局，不需要动。
  12. 绑定远程仓库 Issues：可选。想让 GitHub/Gitee/GitLab/Gitea 的 Issue 自动变成任务时再打开。
  13. 技术栈 / 本地运行 / 测试：填完路径后 Orcsy 会自动探测并预填，你可以修改。这些内容会写进 AGENT.md，让 AI 少走弯路。
  14. 启用该项目：保持打开。

点「保存」。你会看到：

  • 项目卡片出现在「看板」页；
  • 项目文件夹里多了 tasks/ 和 AGENT.md（如果原来没有）；
  • 卡片上显示项目路径、任务统计、git 或 非 git 标记。

6.2 项目卡片上的标记

标记 含义
git 项目是 Git 仓库；默认改动经审查后增量落地工作区、由你确认提交（commit_and_merge 开启时才自动提交/合并/推送）
非 git 项目不是 Git 仓库，Agent 会直接改文件，但不会自动提交
缺指引 项目里没有 AGENT.md，建议点「AGENT.md」补上
自动拉取 Nmin 已开启定时拉取 Issue，每 N 分钟一次
开关 项目启用/停用。停用后调度器会跳过它，配置和文件都保留

6.3 什么是 AGENT.md，为什么它很重要

AGENT.md 是这个项目的「员工手册」。AI 每次做任务前都会先读它。

里面通常写：

  • 项目技术栈（用什么语言、框架）；
  • 怎么本地运行；
  • 怎么跑测试；
  • 代码风格和规范；
  • 哪些事情绝对不能做；
  • 什么情况下应该停下来求助（blocked）。

新建项目时 Orcsy 会自动生成一份英文模板，并根据探测结果填入 Stack / Run / Test。你可以点项目卡片上的「AGENT.md」直接编辑，改成中文、补充项目约定都可以。

💡 想让 AI 表现更稳定，最值得花时间的就是把 AGENT.md 写清楚：测试命令、代码规范、不要碰的目录、完成标准。

6.4 项目级可选设置

在项目卡片点「设置」可以修改：

  • 项目名、路径、任务目录、指引文件；
  • 每轮任务数、轮数上限、工作分支、命令白名单（轮数上限可填 -1 = 不设上限，靠防死循环护栏兜底）；
  • 专属模型；
  • 访问权限；
  • 工具开关覆盖；
  • 远程仓库绑定与自动拉取间隔；
  • 启用/停用。

修改项目名会同步更新绑定到该项目的技能，不会丢失。

小提示：改完设置保存时不必等任务跑完——配置会立即生效并在下一轮调度自动应用，正在执行的任务不受影响。

7. 创建和管理任务

7.1 最快的方式：卡片上的快速添加

在「看板」页的项目卡片里：

  1. 在「新任务标题，回车快速添加」输入框里写一句话；
  2. 选择优先级（默认 P2）；
  3. 点「添加」或直接按回车。

任务 ID 会自动生成，格式是 优先级-标题，例如 P2-修复登录页错位。重复时自动加 -2、-3。

7.2 完整方式：新建任务对话框

点项目卡片下方的「新建任务」，可以填写更多信息：

字段 说明
任务 ID 留空自动生成；也可以自己起一个英文短名，例如 fix-login-timeout
优先级 P0 最高，P4 最低
标题 一句话说明要做什么
标签 逗号分隔，例如 bug, ui，只用于分类和展示
指派 留空表示任意 Agent 都可以领；填写项目名则只有对应 Agent 处理
任务描述 Markdown 正文，写现象、复现步骤、验收标准

点「保存」后任务进入 open（待办）状态。

⚠️ 只有「待办」状态的任务可以直接编辑。执行中、受阻、已完成的任务点开是只读查看；想改内容，先点「重新入队」把它变回待办。

7.3 优先级怎么选

优先级 什么时候用 例子
P0 线上事故、阻塞所有人的问题 支付接口 500、程序启动即崩溃
P1 重要功能坏了，或本周必须完成 登录失败、核心流程报错
P2 普通需求、一般 Bug（默认） 加一个筛选框、修复样式错位
P3 可以排期、不着急 补文档、优化日志文案
P4 有空再做 代码清理、体验优化

排序规则：先按优先级 P0 → P4；同一优先级内，按你在看板上拖拽的顺序。受阻后重新入队的任务，下一轮会优先领取。

7.4 任务文件长什么样

用文本编辑器打开 tasks/P2-修复登录页错位.md，会看到：

---
title: 修复登录页错位
priority: P2
status: open
labels: [bug, ui]
assignee:
---

## 现象

在 125% 缩放下，登录按钮溢出卡片右侧。

## 复现步骤

1. Windows 显示设置改为 125%；
2. 打开登录页；
3. 观察按钮位置。

## 验收标准

- [ ] 100% / 125% / 150% 缩放下布局正常
- [ ] 不改变现有登录流程

你可以直接改这个文件，保存后看板下一轮刷新就会显示新内容。

💡 任务正文里不要写密钥、密码、内部地址。任务文件会进入 Git 仓库，可能被提交。

7.5 任务状态与生命周期

open（待办）
  │  Agent 领取
  ▼
in_progress（执行中）
  │
  ├── 完成 ──▶ done（已完成）──▶ 自动移动到 tasks/done/
  ├── 受阻 ──▶ blocked（受阻）──▶ 等你处理，可「重新入队」
  └── 手动停止 ──▶ cancelled（已取消）──▶ 要重跑时把任务文件 status 改回 open
状态 看板显示 你可以做什么
open 待办 编辑、删除、拖拽排序
in_progress 执行中 查看、强制停止、标记完成（不推荐）
done 已完成 查看；自动归档
blocked 受阻 查看原因、重新入队、删除
cancelled 已取消 查看、删除；要重跑时把任务文件里的 status 改回 open（或复制内容新建任务）

7.6 任务列表上的操作

操作 在哪里 作用
点击任务行 看板任务列表 待办任务打开编辑；其它状态只读查看
拖拽任务行 / ▲▼ 按钮 任务列表 调整同一优先级内的顺序，同时决定 Agent 领取顺序（手机上用行内 ▲▼ 触屏按钮）
勾选任务 任务行左侧 批量选择
全选本页 列表上方 选中当前页 10 个任务
批量删除 选中后出现 删除选中的任务文件，不可恢复

标记完成 待办/执行中任务 手动把任务标为完成，并归档到 tasks/done/（与 Agent 完成同一落点，立即出现在「已归档」列表）
强制停止 执行中任务 立即中止 AI 循环和正在跑的命令，丢弃临时改动，标为已取消

⚠️ 「删除」「清空」「强制停止」都不可撤销。删除任务文件前建议先确认内容；Git 项目强制停止会丢弃本次任务在临时副本里的改动，非 Git 项目已改的内容会留在目录里。

7.7 已归档任务

任务完成后会自动移动到 tasks/done/。项目卡片底部的「已归档（N）· 点击查看详情」可以展开查看，点任务行只读查看内容。

7.8 写好任务的 5 个技巧

  1. 写清楚「现在是什么样」：报错信息、截图描述、复现步骤。
  2. 写清楚「做成什么样算完成」：用验收标准列表，越具体越好。
  3. 限定范围：告诉它只改哪个页面/模块，不要顺手重构整个项目。
  4. 一次只做一件事：大任务拆成多个小任务，成功率和可审查性都更高。
  5. 提供验证方法：例如「运行 npm test」「打开 /login 页面检查」。

一个反例（太模糊）：

优化一下登录。

一个正例：

登录页在 125% 缩放下按钮溢出卡片。请只调整登录页样式，不改登录逻辑。验收：100%/125%/150% 三种缩放下按钮完整显示，npm run build 通过。

8. 让 Orcsy 开始工作

8.1 两种触发方式

  • 定时调度：程序每隔一段时间自动扫描一次。默认 300 秒，可在设置页改（30~86400 秒）。
  • 立即扫描：点顶部「▶ 立即扫描」，马上执行一轮。适合刚加完任务想立刻看结果。

两者不会重复领取任务：同一时间一个项目只有一个 Agent 在工作。

8.2 看板顶部状态条

标签 含义
调度空闲 / 扫描执行中… 当前有没有在跑扫描
已完成周期 N 从启动到现在跑了多少轮
上次扫描 刚刚 / N 分钟前 最近一次扫描时间
扫描间隔 Ns 当前设置的间隔
项目名：处理 N 任务 上一轮每个项目处理了几个任务

8.3 任务执行时发生了什么

  1. Orcsy 扫描项目 tasks/，挑出 status: open 的任务；
  2. 按优先级和顺序领取一个；
  3. 把状态改成 in_progress；
  4. 如果项目是 Git 仓库，在项目下创建临时工作副本 .worktree-arranger/；
  5. AI 读 AGENT.md 和任务内容，开始读文件、改文件、跑命令；
  6. 每轮操作都会往任务文件的「## 执行进度」追加一行，进程被强杀也不丢；
  7. AI 报告完成后：
    • 成功：系统提交、合并回主分支；配置了远端则推送；任务标 done 并归档；
    • 受阻：丢弃临时副本，任务标 blocked，写明原因；
    • 取消：丢弃临时副本，任务标 cancelled。

Git 项目才有临时副本；非 Git 项目没有这层隔离，Agent 已做的修改会留在项目目录里，受阻/取消后请自行检查或还原。

8.4 看运行日志

看板底部的「运行日志（从新到旧，点击收起）」会显示：

  • 每轮扫描开始/结束；
  • 每个任务的开始/结束、提交号、受阻原因；
  • 模型思考内容（如果开启）会折叠成紫色条目，点开可看。

页面每 5 秒自动刷新。日志同时写入 logs/orcsy.log。

💡 任务详情 →「运行记录」→ 点击 run_id 可展开全过程事件流：每轮模型正文、思考摘要、计划调用、工具结果逐条可查。

8.5 任务结束后

  • 成功：任务行变「已完成」，进入归档；项目多一条 Git 提交；
  • 受阻：任务行变「受阻」，点开可看「Agent 处理结果」里的原因；
  • 取消：任务行变「已取消」；要重跑就把任务文件里的 status 改回 open。

如果开启了提醒，完成/受阻时会有提示音和托盘气泡；手动停止不会提醒。

10. 进阶功能：审批、技能、Issues、镜像源

10.1 人工审批（访问权限模式）

默认是「完全访问」，AI 做任何操作都不询问。想更安全，可以在设置页改：

模式 适合谁 会询问什么
ask_on_change 变更前询问 第一次用、对 AI 不放心 写文件、改文件、批量改、删文件、移动文件、执行命令
autonomous 自主模式 有经验、只想拦住高风险操作 删文件、移动文件、执行命令
full_access 完全访问（默认） 信任 AI、追求效率 不询问

工作方式：

  1. AI 要做敏感操作时，任务会挂起（操作不执行，零副作用）；
  2. 顶部出现「🔔 待审批 N」；
  3. 点开可以看到：项目、任务、工具、参数预览、已等待时间；
  4. 你可以「批准」或「拒绝」；
  5. 勾选「本任务内始终允许该工具」可以减少重复确认（只对当前任务有效）；
  6. 超过审批超时（默认 30 分钟）没人处理，会自动拒绝，任务不会永久卡住。

拒绝和超时都会告诉 AI「为什么不行」，让它调整方案或按受阻收尾。

10.2 工具开关与命令白名单

工具开关决定 AI 能用哪些能力。默认全开（finish 是结束任务的协议工具，永远可用）。

常见用法：

  • 不想让 AI 联网：关闭 web_fetch；
  • 只让 AI 改代码、不跑命令：关闭 run_command；
  • 只想让 AI 审查、不改文件：关闭写/改/删/移类工具。

命令白名单决定 run_command 能执行哪些命令。默认包含 python、pytest、node、npm、cargo、go、dotnet、git、包管理器、常用只读命令等。关闭某个命令后，AI 调用会被直接拒绝。

项目级可以覆盖全局设置：项目对话框里打开「覆盖 Agent 工具开关」，逐项设置。删除覆盖即回到跟随全局。

10.3 技能库（Skill）

技能是给 AI 的「专项工作手册」。例如：

  • 项目的编码规范；
  • 某个框架的最佳实践；
  • 发布流程；
  • 环境安装指南。

四种来源：

  1. 内置 env-setup：首次启动自动放入，教 AI 在缺少语言/工具链时自动安装；
  2. 扫描 AI 工具：把 ZCode / Claude Code / Codex / OpenCode 等工具里已有的技能批量导入；
  3. 导入本地技能：选择一个包含 SKILL.md 的目录；
  4. 新建技能：在看板里直接写名称、描述、正文。

技能的作用范围：

  • 全局：所有项目都能用；
  • 专属·项目名：只有该项目能用。

注意：

  • 技能存放在数据目录的 skills\ 里，不会写进项目目录；
  • 系统提示词里只放「名称 + 描述」索引，AI 需要时再用 read_skill 读取全文，所以技能多也不会撑爆上下文；
  • 删除外部导入的技能，只是删除 Orcsy 里的副本，原工具目录里的样本还在，可以重新扫描找回；
  • 删除自建技能不可恢复。

10.4 Issues 自动导入

如果你把项目托管在 GitHub / Gitee / GitLab / Gitea，可以让 Issue 自动变成任务。

配置步骤：

  1. 项目「设置」→ 打开「绑定远程仓库 Issues」；
  2. 填仓库 URL，例如 https://github.com/owner/repo；
  3. 选择平台（自托管 GitLab/Gitea 必须手动选）；
  4. 填认证信息：
    • token（推荐；GitHub 只支持 token）；
    • 或账号 + 密码（GitLab / Gitee / Gitea 支持）；
  5. 可选：填自动拉取间隔（分钟，0 表示只手动拉取）；
  6. 保存。

使用：

  • 项目卡片点「拉取 Issues」→ 把 open 状态的 Issue 导入任务队列；
  • 优先级默认 P2；Issue 带 P0~P4 标签时按标签；
  • 任务文件带来源标注，已导入过的（包括已归档）不会重复导入；
  • 单向导入：Orcsy 不会把任务状态写回 Issue。

10.5 镜像源与国内网络

如果你在国内、没有代理，下载依赖可能很慢或失败。Orcsy 提供了三层兜底：

  1. 镜像源测速：设置页「🪞 镜像源管理与测速选源」→ 点「测速全部源」→ 点「应用最快源到环境变量」；
  2. 环境变量：在「Agent 子进程环境变量」里填 GOPROXY、PIP_INDEX_URL、npm_config_registry、HTTP_PROXY 等；
  3. env-setup 技能：AI 发现缺少工具链时，会按技能自动安装；包管理器失败时自动切换国内镜像直下。

镜像源类别包括：Go 安装包、Go 模块代理、npm registry、pip index、Node.js 安装包、JDK、Python 安装包。你可以禁用不想要的源，也可以添加自己的内网镜像。

⚠️ 「应用最快源到环境变量」会覆盖你手动填的同类环境变量。应用后请检查一下文本框内容。

10.6 多项目、并行与专属模型

  • 每个项目一个 Agent，互不干扰；
  • 设置页「并行 Agent 数」大于 1 时，多个项目可以同时执行（1~16）；
  • 同一个项目同一时间只做一个任务；
  • 项目可以绑定专属模型：例如简单项目用便宜模型，复杂项目用强模型；
  • 专属模型只覆盖你填的字段，没填的自动继承全局。

10.7 通知

设置页「🔔 提醒设置」：

  • 提示音：完成播内置「叮咚」音，受阻播内置警示音（音频缺失时回退 Windows 系统音）；
  • 系统通知：托盘气泡，看板没开也能收到；
  • 手动停止（取消）不提醒；
  • 用 --no-tray 启动时没有托盘，系统通知没有渠道。

10.8 数据脱敏（敏感信息不出本地）

Agent 干活时会读工作区文件、执行命令、接收任务描述——如果里面有 API 密钥、数据库密码，默认会随请求原文发给你配置的模型厂商。数据脱敏在发送前把这些内容在本地掩除：

  • 处理只在内存中进行：不写临时文件、不进日志，任务结束立即清除映射，任何时刻磁盘上没有脱敏数据副本；
  • 高置信规则默认开启：只掩格式自证敏感的令牌——sk- 系 API key、GitHub/GitLab 令牌、AWS/Google/Slack 密钥、JWT、PEM 私钥块、Bearer 认证头、URL 里的 token= 参数、数据库连接串密码段；
  • 占位符可读：模型看到的是 [REDACTED:api_key:a1b2c3d4] 这样的占位符，能区分多个不同密钥；
  • 写回自动还原：模型把占位符写进文件（如「把密钥复制到 CI 脚本」「改 .env 后整文件回写」）时，落盘前自动还原为真实值——复制密钥类任务照常完成；
  • finish 结论保持脱敏形态：任务总结里出现的是占位符，密钥不会写进任务文件；
  • 键值对增强规则默认关闭：api_key=xxx、"password": "xxx" 这类规则覆盖面广，但文档示例、测试夹具里的假密钥也会被替换（模型会读到占位符而非原文），确认工作区没有这类内容再开启；
  • 自定义正则：单位内部约定格式的令牌（如 PROJECT_SECRET_xxx）可以加自定义正则，每行一条，保存立即生效。

在看板「设置 → 🛡 数据脱敏」调整，也可以在 config.yaml 的 masking 节配置（enabled / enhanced_rules / custom_patterns）。

10.9 自动更新与重启

  • 启动时自动检查更新（可关）；
  • 顶部「检查更新」→ 有新版本时点「更新到 x.y.z」；
  • 更新源仓库 URL 支持 Gitee 与 GitHub（设置页「🔔 通知与应用 → 应用」，0.32.0 起）：默认官方 Gitee 源，可改成自己的 GitHub 仓库镜像（如 https://github.com/xxx/orcsy）；私有仓库在旁边填访问令牌（GitHub 用 Personal Access Token）；
  • 更新包在后台静默安装，程序自动重启，页面自动刷新；
  • 装在 Program Files 等系统目录时，会弹一次 UAC 授权；
  • 更新失败会自动回滚，并打开安装日志；
  • 也可以「手动导入本地安装包」：选择 orcsy-update-*.zip，支持同版本覆盖、升级、降级；
  • 更新包按当前程序架构选择：ARM64 原生版只领 orcsy-update-*-windows-arm64.zip；某版本未提供 ARM64 包时会明确提示，不会把原生程序悄悄替换成 x64 仿真版。

⚠️ 降级注意（运行台账）：运行台账是 0.25 起的新能力，涉及 runlog 配置节与 runs/ 目录。旧版本不认识该配置节：降级后不要在旧版本里修改台账相关设置（保存任意设置可能把 runlog 节连同自定义目录一起写丢）；台账数据文件不会被删除。降级前请备份 config.yaml 与台账目录；升级回新版本后，程序会按配置和上次运行目录自动接回历史记录。

10.10 看板登录密码

默认只监听 127.0.0.1，只有本机能访问，不需要密码。

如果你要：

  • 用 --host 0.0.0.0 让局域网访问；
  • 用 Docker / systemd 部署到服务器；
  • 通过反向代理暴露到公网；

必须设置登录密码。非回环地址 + 空密码时程序会拒绝启动；如果绕过这层保护对外暴露，任何能访问端口的人都能操作看板、改配置、启停任务（密钥只显示掩码，但仍可被替换）。

设置与重置位置：

  • 设置页「⚙️ 应用」→「看板访问密码」（留空保持 / 输入即改 / 清除即关鉴权，独立保存、与调度/端口/日志保留解耦）；
  • 密码在 config.yaml 中一律采用 PBKDF2-HMAC-SHA256 (100,000 次加盐哈希) 密文安全存储，明文不入库；
  • 忘记密码时：管理员登录服务器在终端运行 orcsy reset-password（或简写 orcsy passwd）即可快捷重置密码（支持交互式隐藏输入），或使用 --clear 清除密码恢复本机免密模式： 
    orcsy reset-password                    # 交互式安全重置（带隐藏输入与二次确认）
orcsy reset-password <新密码>            # 命令行直接指定新密码
orcsy reset-password --clear            # 清除密码，切回本机免密访问

设置后打开看板会先出现登录页：输入密码 → 点「登录」。顶部右侧会出现「退出」按钮。

行为：

  • 登录后会话有效期 7 天；登录页勾选「记住这台设备」时 30 天（手机远程访问少掉登录）；
  • 登录成功同时下发会话 Cookie 与 Bearer Token 双凭证：Cookie 丢失（移动端反代/切网）时 Token 仍保持登录；
  • 程序重启后需要重新登录；
  • 修改密码后所有旧会话立即失效；
  • 鉴权不替代 HTTPS。公网部署请再套一层反向代理（nginx / caddy）上 HTTPS。

10.11 日志、开机自启与端口

日志

  • 看板底部的「运行日志」只显示最近一段，完整日志在数据目录的 logs/orcsy.log；
  • 设置页「⏱ 调度与看板」可以设置：

    • 日志总占用上限（MB）：默认 200，活动日志 + 备份 + 归档合计超限时从最旧的删起；0 表示不限制；

开机自启

  • 设置页「⚙️ 应用」→ 打开「开机自动启动」；
  • 写入当前用户注册表，不需要管理员权限；
  • 托盘菜单里也有「开机自启动」勾选项；
  • 不想要自启时，关掉开关即可。

看板端口

  • 设置页「⏱ 调度与看板」→「看板端口」；
  • 保存后下次启动生效；
  • 也可以用命令行 --port 8080 临时覆盖；
  • 端口冲突时的行为见 12.1。

10.12 任务审查（Review Agent）：第二个模型把关

Orcsy 支持在任务完成后、合并归档前，由一个独立的审查 Agent（与执行任务的 Agent 不是同一个模型）检查任务成果：对照需求与验收标准抽查实现、（可选）实际跑测试验证。审查通过才合并主分支并归档；不通过则带着问题清单自动返工。

默认状态：审查未启用。 没配置审查模型时一切照旧（任务完成即合并归档）。想开启，只需要给系统配置第二个模型（可以是便宜的小模型）：

  1. 打开设置页「🔍 任务审查（Review Agent）」卡片；
  2. 填写审查模型的 provider / base_url / api_key / model（点「获取模型列表」可拉取候选）；
  3. 保存。审查门即刻对全部项目默认生效（某个项目不想要时，在该项目「设置」→「审查 Agent」里单独关闭）。

硬性规则：审查模型不能与任务模型相同。 任务模型在设置页「大模型接入」配置（项目可绑定专属模型）；审查模型与之同名时保存会被拒绝——两个不同的模型交叉验证，防止「自己审查自己」。

审查是怎么工作的：

  • 任务 Agent 报告完成后，改动先提交到工作分支（还不合并）；
  • 审查 Agent 只读核查代码：对照任务里的验收标准逐条检查，「允许执行测试命令」开关打开时（默认）会实际跑测试验证；
  • 通过 → 自动合并主分支 → 归档到「已完成」；
  • 不通过 → 任务带着审查意见自动返工（意见写在任务正文里，执行 Agent 下轮直接看到）；返工次数默认 2 次（全局可调 1~10，项目可单独设置），用完转「受阻」等人工裁决——此时成果保留在工作分支上，可以人工检视或手动合并；
  • 审查中途程序被关掉也没关系：改动已经提交在分支上，下次启动自动补审，不会重跑任务。

返工与提交： 返工过的任务通过审查后，多次返工的提交会自动收敛为一个提交再合并（「返工通过后收敛提交」开关，默认开），保持主分支历史整洁。

数量上限怎么填： 返工次数（全局默认 2 次）与单任务轮数上限（max_agent_turns）都支持填 -1 = 不设上限：

  • 返工次数填 -1：审查不通过就一直返工，不会自动转「受阻」（适合"必须改到通过"的场景，注意会持续消耗 token）；
  • 轮数上限填 -1：任务可以跑任意多轮。系统仍有防死循环护栏兜底（同一文件被反复读超过 5 次自动拦截；代码类角色连续 20 轮只读不写会强制熔断；连续 3 轮不调工具视为卡住收尾），所以不会无限空转，但长任务确实可能跑很多轮。

看板上的标记： 任务卡片上 🔍 待审查 表示已完成正在审查或等待补审；🔍 返工 ×N 表示被审查退回过 N 次。项目卡片上会显示「审查开启 / 审查关闭 / 审查模型冲突」状态。

成本提示： 审查每次约消耗 3~8 轮只读调用的 token，在设置页「用量统计」里按审查类单独记录，可与执行消耗分开核算。

10.13 多模型 Agent 项目小组（Project Team）协同

Orcsy 0.22.0 引入了多模型 Agent 项目小组（Project Team）。用户可以自由组合多个不同专长大模型的 Agent 组成研发团队进驻任意项目，完成复杂需求的分工协作：

  • 👑 项目经理（PM）：只读摸底项目代码库与架构，将需求拆解为职责明确的子任务并使用 depends_on_refs 编排 DAG 有向无环依赖图；或对简单单端任务直接调用 reassign_task 转派下游。
  • ⚙️ 后端 / 🎨 前端开发工程师：在按任务隔离的 Git Worktree 沙盒中专注本端编码与单测，Prompt 自动透传前置依赖任务的交付物摘要（接口契约）。
  • 🧪 测试工程师（QA）：拉起本地服务与无头/桌面浏览器进行端到端联调测试；发现缺陷调用 report_bug 派发 Bug 修复任务，原测试任务自动挂靠依赖并进入等待回归状态，待前后端修复后自动唤醒 QA 开展多轮回归测试。
  • 🛡️ 强制 Worktree 沙盒隔离 + 人工把关最终提交：所有写代码角色按任务在独立 worktree（.worktree-arranger/<任务ID>，分支 orcsy/task/<项目>/<任务ID>）中编码，通过审查后仅增量合入主分支工作区（未提交状态），默认绝不自动执行 git commit 与 git push，最终提交权 100% 留给人把关（见 10.14 人工把关提交）！
  • 🧠 并发子代理探索（delegate_explore）：项目经理与各开发角色都能在开工摸底时一次派生 2~4 个只读子代理，并行调研数据层、路由、鉴权、既有测试等不同模块，单轮拿到汇总报告，显著压缩串行翻阅文件的耗时。子代理严格只读、有扇出与轮数上限、同样受「强制停止」约束。
  • ⚡ 按厂商配额自适应并发（subagent.max_parallel / adaptive）：真正打给厂商的在途请求数受「子代理并发预算」约束（默认 4，与单次派 4 个子代理的熔断值无关）。厂商从不公开并发上限，所以默认开启自适应：撞到 HTTP 429 立即对半降并发并让整个配额池静默（优先按 Retry-After 等待），连续成功后逐步爬回；低配额套餐下表现为「变慢」而不是「部分子代理失败」。同一 base_url + api_key + model 共享一个预算池，多个项目并行时也不会各限各的。
  • 📦 拆分完成即归档：PM 完成需求拆解并派发后，父任务标记为「已完成」自动归档到 tasks/done/，活跃列表只保留接力的子任务，看板不再堆满已拆完的原任务。
  • ⚡ 同周期链式推进（chain_within_cycle）：依赖解锁后毫秒级连续接棒推进下一阶段，单个需求无需跨越多个 300 秒调度周期即可完整闭环。
  • 🛠️ 运维/DevOps 工程师（devops，0.31.0）：专职容器化与交付面——Dockerfile、docker-compose、CI/CD 流水线脚本、K8s 声明与环境配置的编写维护。可写代码（产基础设施文件），沿用项目既有镜像/registry/tag 约定，严禁在清单中写明文密钥。
  • 👁️ UI 视觉审查专家（ui_critic，0.31.0）：只读视觉把关角色——拉起前端服务后用浏览器截图/快照对页面排版、间距、响应式缩放做纯审美审查；发现视觉缺陷逐条 report_bug 定级（blocker/major/minor）派给前端修复，自身不改业务源码，报完 Bug 自动进入等待回归。
  • 🔒 安全合规审计工程师（security，0.31.0）：只读安全审查角色——聚焦本次变更范围做静态扫描与依赖 CVE 检索，追踪「用户输入 → 危险汇点」数据流（SQL 注入、越权、硬编码密钥）；确认的风险逐条 report_bug 附攻击场景与修复建议，无实证的理论问题不得定为 blocker。
  • 👥 双层配置复用：全局设置页「👥 多模型项目小组 (Team)」一次配置各角色专属模型 + 项目设置弹窗自由引用与局部技术栈微调；每个角色都内置一套职责规范提示词模板（可一键载入或自定义）。

老版本升级后如何加入三个新角色（0.31.0 的 devops / ui_critic / security）： 升级只扩充了「可选角色清单」，老配置的预设池仍是原四个默认预设——按需两步接入： ① 补预设（可选）：设置页「🤖 模型与团队 → 多模型项目小组」点 「补齐内置角色预设（devops / ui_critic / security）」，三个内置预设（带职责模板与默认轮数）进入草稿，模型默认继承全局，检查后点「保存角色预设池」生效； ② 进驻项目：项目「设置 → 多模型 Agent 项目小组」里点 「+ 添加成员」，角色类型下拉选对应角色即可（新建项目的默认成员名单已含三者）。不建预设直接加成员也可以——模型与工具走角色内置默认，可再在成员卡里微调。

只读验证角色语义：ui_critic / security 与 QA 同属「只读验证型角色」—— 通过 report_bug 报出缺陷后任务保持打开进入等待回归（不会误归档 done）； 验收通过无文件改动时正常完成（不误判空转 blocked）。

10.14 本地调试与 Chromium 浏览器自动化（Local Debug）

针对 Web 与 API 项目，Orcsy 内置了基于 CDP 协议的本地调试工具链（测试工程师 QA 默认开启，开发角色按需可选）：

  • Chromium 浏览器自动化（browser_*）：通过纯 Python CDP 直连本地安装的 Google Chrome 或 Microsoft Edge（零外部 driver 依赖），支持元素结构化文本快照、按 ref 寻址点击与输入、页面等待、截图落盘及 Console/Network 日志监听；
  • 开发服务管理（dev_server_*）：任务中后台常驻启动 dev server（自动分配空闲端口并等待就绪），任务结束自动清理释放子进程；
  • 本地接口调试（http_request）：受控放行本地/局域网 HTTP API 调试（Cookie 会话保持，受主机白名单严格约束，杜绝内网穿透）。

10.15 人工把关提交（待人工提交 → 独立审查页）

开启项目小组或 Worktree 隔离后，Agent 的成果只会增量落入主分支工作区，不会自动 commit / push。项目卡片上出现红色 「待人工提交 N」 按钮时，点它进入独立的人工把关提交页（新标签页 #/commit?project=项目名，不再是弹窗）：

左：改动文件清单

  • 列出全部未提交改动；点击任一文件，右侧立即显示它的 diff；
  • 包含嵌套 gitlink 子仓库（如 caresy 的 caresy-api、caresy-web）时，按仓库分组展示，数量为各仓库真实文件数之和；
  • 每行右侧两个动作：排除（不提交、保留在工作区）与 删除；
  • 列表头提供批量操作：排除临时产物 N、删除临时产物 N；排除/删除都只作用于该文件所属仓库。

右：代码 diff 对比

  • 默认自动换行：超长代码行折行完整显示，不会横向被切掉；右上「自动换行」可切到「不折行 + 横向滚动」；
  • 顶部显示 「N 行 · X KB」，以及 「下载补丁」 按钮（导出该文件完整 .patch）；
  • 单个文件改动极大（超 100 万字符）时会提示「预览已截断」，用「下载补丁」可拿到完整内容。

排除 vs 删除（都是为了让临时测试产物不进主分支）

操作 未跟踪的新文件/目录（如 test-output.log、__pycache__/） 已跟踪的文件（如修改过的源码）
排除 不提交，保留在工作区，稍后仍可恢复提交 不提交本次修改，保留改动在工作区
删除 物理删除（目录递归删除，不可恢复） 还原到 HEAD（撤销本次修改，文件本身保留）
  • 自动识别临时/测试产物：*.log、*.tmp、*.temp、*.orig、*.rej、*.bak、*.pyc、__pycache__/、.pytest_cache/、.mypy_cache/、.ruff_cache/、node_modules/、coverage/、htmlcov/、.nyc_output/、.coverage、tmp/、.DS_Store 等；不会误判 *_test.go、*.spec.ts 这类真实测试源码；
  • 所有删除都会先弹二次确认，列出将被处理的文件，确认后才执行。

提交

  • 填写 Commit Message；勾选「同时推送到远程仓库」则额外执行 git push origin；
  • 点 「确认提交所有仓库」 → 只提交未被排除的文件；提交后主工作区恢复干净，内部 stage 分支自动同步；
  • 含嵌套子仓库时自动编排：子仓库先提交 → 父仓库最后提交更新后的 gitlink 指针；推送也是子仓库先推，全部成功后才推父仓库（子仓库推送失败或未配置远端时父仓库不推送，避免远端指针悬空）；
  • 所有仓库共用当前填写的 Commit Message；页面顶部会显示本次实际提交的仓库数与文件数；
  • 如果还有被排除的文件，页面会留在原处并明确提示「已排除 N 个文件未提交（保留在工作区）：…」，方便你继续处置；
  • 全部文件都被排除时，「确认提交所有仓库」按钮会禁用，避免产生空提交。

这个页面就是交付流程的最后一道人工闸门：Agent 永远不会替你 commit / push，最终提交权始终在你手里。

10.16 移动端远程访问（手机看板 / PWA）

Orcsy 支持在手机浏览器上远程查看、编辑与新建任意项目的任务——适合外出巡检时盯进度、任务受阻时随手补一句话、灵感来了立即录入排队。

第一步：开放访问 + 设置密码

最省事的方式：桌面看板右上角点 「📱」按钮（移动端在底部导航「更多」的抽屉菜单里）打开「手机远程连接」向导—— 看板还只监听本机回环时，向导会给出 「一键开放手机访问」 勾选项：打勾并确认后自动改配置 （web.host: 0.0.0.0 + 自动生成强密码，只存密文）落盘并自动重启应用；重启后登录页会再提示一次 访问密码，复制登录即可。

也可以手动改：config.yaml 里把 web.host 改为 0.0.0.0（监听全部网卡）并设置 web.auth_password， 重启生效。向导未开启时列出所有可达地址、生成扫码二维码、一键复制地址；重启后终端也会打印局域网地址 与手机扫码二维码。

第二步：手机连接

  • 手机与电脑连同一 Wi-Fi，用相机扫码（或输入地址）直达看板，输入登录密码即可；
  • 登录页勾选 「记住这台设备（30 天免重复登录）」：签发 30 天长会话 + Bearer Token 双凭证，手机息屏、切网、反代丢 Cookie 都不容易掉登录；
  • 跨网访问可用反向代理（Nginx / Caddy 上 HTTPS）、FRP / Tailscale / Cloudflare Tunnel 内网穿透，或直接部署在公网服务器；配置 web.public_url 后向导与终端会优先展示你的公网域名。

手机端专属界面（屏幕宽 ≤ 768px 自动切换，桌面布局不变）：

  • 极简吸顶顶栏：只留待审批徽标与刷新，低频操作全部收进抽屉菜单；
  • 底部导航栏：看板 / 项目 / ＋ 新建（选项目后呼出全屏新建抽屉）/ 更多（抽屉菜单：导航、主题切换、扫描、重启、退出等都在这里）；
  • 任务全屏抽屉：新建/编辑任务时「保存 / 取消」固定在最顶端——软键盘顶起也不会挡住按钮；正文框上方有 Markdown 快捷工具条（标题、待办、列表、粗体、代码块）；
  • 触屏排序：任务卡片上的 ▲▼ 按钮，同一优先级分组内上移/下移（替代桌面拖拽）；
  • 草稿防丢：编辑中每 0.3 秒自动暂存到本机；来电、切后台被杀后重开，提示「检测到未保存的草稿」一键恢复；
  • 防冲覆盖：保存任务时后端做乐观锁校验——后台 Agent 刚改过这个任务时返回 409 冲突，弹出「保留我的修改 / 采用最新状态」由你决定，绝不静默覆盖 Agent 的回写；
  • 弱网低耗：手机息屏自动暂停轮询，回到前台立即静默刷新；移动端轮询走轻量摘要（省略日志尾部与归档），蜂窝流量从 ~80KB/次压到几 KB；运行日志改为点开时按需加载；
  • 添加到主屏幕（PWA）：手机浏览器菜单里「添加到主屏幕 / 安装」，Orcsy 会像独立 App 一样全屏打开（带图标与启动画面）。

反向代理部署（可选）：Orcsy 收到的对端 IP 恒为反代地址时，登录限速按 web.trusted_proxies 名单解析 X-Forwarded-For 里的真实客户端 IP——默认信任本机回环（同机 Nginx/Caddy/FRP 场景开箱即用），不会因为封禁 127.0.0.1 把本机也锁在门外。

10.17 预算与成本上限（Budget Guard）

在「设置 → 预算与成本」开启，或在 config.yaml 的 budget 节配置（默认关闭）：

  • 单任务 token 上限：prompt + completion 累计达到上限即停止执行；
  • 单任务成本上限：按 budget.prices 里的模型单价折算人民币；没配单价的模型不计算成本；
  • 项目当日上限：按本地自然日累计，用尽后调度器暂停该项目的新任务（正在跑的任务允许收尾）；
  • 超限不是失败：任务标「受阻」、frontmatter 写入 block_reason: budget_exceeded，worktree 成果保留；调高预算或等次日点「重新入队」即可续跑；
  • 用量存 state/budget.json，只统计开启预算后产生的模型调用；
  • 单价表示每百万 tokens 的人民币价格：
budget:
  enabled: true
  max_tokens_per_task: 300000
  max_tokens_per_project_per_day: 5000000
  prices:
    deepseek-chat: {prompt: 1.0, completion: 2.0}

10.18 熔断停机与恢复

在「设置 → 熔断与恢复」开启/调整（默认开启），或配置 config.yaml 的 resilience 节：

  • 连续失败阈值：同一项目连续 N 次失败后暂停（默认 3）；
  • 窗口失败率：最近 N 分钟内失败率达到阈值且样本足够时暂停（默认 120 分钟 / 60% / 至少 5 个样本）；
  • 触发后项目暂停领取新任务，正在跑的任务允许收尾；项目卡片显示「已熔断」与原因；
  • 默认必须人工点「恢复」；勾选「窗口结束后自动恢复」则暂停满一个窗口后自动恢复一次；
  • 预算超限、任务被改写（stale_lease）、用户强制停止不计入失败，避免误熔断。

10.19 写操作审计

看板「设置 → 审计日志」可查看最近的写操作记录（只读）：

  • 覆盖：登录成功/失败、退出、任务增删改/排序/停止、设置保存、项目增删改、提交确认、改动丢弃、Issues 拉取、审批响应、技能/镜像/更新、熔断恢复、API Key 写调用；
  • 每条记录：时间、动作、操作者（user / api_key:哈希前缀 / local）、IP、对象、结果；
  • 参数只记摘要（状态码、键名），不记录密码、API Key、仓库 token 或任务正文；
  • 完整日志在数据目录 logs/audit.jsonl，单文件超过 5MB 自动轮转，保留最近 5 份；
  • 直连改 config.yaml 或任务文件不会经过看板，因此不会出现在审计里（Git/文件系统是最终事实源）。

10.20 出网白名单

应用自身发起的 HTTP 统一经出口白名单判定：模型调用、Issue 拉取、镜像测速、网页抓取、更新检查与更新包下载。配置在「设置 → 工具与网络 → 出网白名单」，或 config.yaml 的 egress 节：

egress:
  mode: allowlist      # allowlist（默认）| off（仅排障：全放行、不写拒绝审计）
  extra_hosts: []      # 追加主机，如 api.example.com / *.example.com / host:8443
  audit: true          # 拒绝时写 logs/audit.jsonl（action=egress.deny）
  • 自动放行：配置里的模型端点、Issue 仓库（含 api_base）、镜像源（内置 + 自定义/禁用清单）、更新源主机，换模型/加项目后自动生效，不用重复填；
  • 回环地址（127.0.0.1 / localhost / ::1）不是出网，始终放行——本机 dev server、浏览器 CDP、测试桩不受影响；
  • 额外主机：web_fetch 要访问的第三方文档站、企业内网代理等，在 extra_hosts 或设置页标签里添加；*.example.com 同时匹配主域与子域，带 :端口 则只匹配该端口；
  • 拒绝表现：模型调用 / Issue / 更新提示「出网白名单拦截」并给出加白路径；镜像测速把该源记为不可达；web_fetch 直接把提示返回给模型；拒绝同时写审计；
  • 不拦截子进程：Agent 的 run_command 启动的 npm / pip / git 等子进程出网无法在应用层拦截，依靠镜像/代理环境变量与运行台账约束；文档不承诺「零外网请求」；
  • 排障：临时把 mode 改为 off（全部放行且不写拒绝审计），定位后改回 allowlist。设置页会显示推导出的主机数、本次进程放行/拒绝计数与最近拒绝记录。

10.21 团队记忆与长上下文处理（Phase 1/2）

架构黑板报 ARCHITECTURE.md

  • 放在项目根目录，记录核心分层、模块边界、技术选型、公共数据模型与关键路由；正文统一用英文书写（接口/路径/标识符保留原文），以节省 token；
  • 每个任务启动时自动只读注入前 3000 字，让不同角色对项目全貌保持共识；文件不存在则不注入；
  • PM 首次拆解需求时用 update_architecture(mode="replace") 创建/更新；开发完成重大接口或数据表变更后用 mode="append" 追加 ≤200 字符的英文增量；普通小改不用维护；
  • 该工具只能写 ARCHITECTURE.md，不会给 PM/QA 开放任意文件写权限。

项目经验记忆 PROJECT_NOTES.md（Phase 2）

  • 与黑板报并列的第二块记忆：测试/构建命令与坑、环境怪癖、依赖约束、易误伤的操作、验证技巧等会长期影响后续任务的经验；
  • 每个任务启动时自动只读注入首尾共 1500 字（前 600 字保留稳定约定 + 末 900 字保留最新经验——新条目追加在末尾，必须可见）；文件不存在则不注入；
  • 任务收尾前，Agent 用 update_project_notes(mode="append") 追加 1~3 行（每条 ≤120 字符，英文优先）；同类条目重复时用 mode="replace" 合并；
  • 与黑板报同款写边界：只能写该文件，单文件上限 8000 字符。任务日志、临时端口/凭证、当次调试过程不写这里；架构事实写黑板报；
  • 写满 8000 字符后 append 会被拒绝并给出可执行指引：先读取全文、归纳成 ≤1500 字摘要，用 update_project_notes(mode="archive", content=摘要) 归档——摘要带日期追加到 LONG_TERM_MEMORY.md，PROJECT_NOTES.md 精简为该摘要，之后可继续追加；
  • LONG_TERM_MEMORY.md 保存历史归档（上限 20000 字符，超出自动裁剪最旧段落）。它不整篇注入，提示词只给一句指引，需要更早的经验时由 Agent 用 read_file 按需读取。

长上下文处理（Phase 2）

  • 对话历史超过软预算（估算 64K tokens；紧急情况下按模型窗口 90% 触发）时仍会裁剪旧工具结果；
  • 裁剪前先向任务模型请求本批结果的 ≤400 字摘要，追加为 【上下文压缩摘要】 消息——已确认的事实（路径、接口、配置值、测试结论、已做修改）不会随占位化丢失；
  • 摘要请求失败时自动降级为确定性摘要（工具名 + 每条结果开头片段），最坏情况与旧行为一致，不会更差；
  • token 估算已修正：非 ASCII（中文为主）按 ~0.7 token/字符计（旧实现约为其一半，对中文低估约 2 倍）。

需求批次共享剪贴板

  • 同一 parent_id 需求树下的 PM 子任务、开发、QA 与 Bug 修复任务属于同一批次；
  • 开发可用 session_share(key, value) 暂存临时端口、测试账号、动态 JWT、临时 DSN；
  • QA 用 session_read(key) 直接读取，key 留空可列出可用键（不返回值）；不再靠日志正则猜；
  • 数据存 <配置目录>/state/session_bus/，不写任务文件、不进 Git；批次全部验收/终止后自动删除，异常残留 7 天过期；
  • 只放临时运行态，不要放长期密钥或大段文本。

依赖成果一键查看

  • 任务详情「前置依赖任务」下会列出每个前置任务的状态（已完成/执行中/受阻/已删除）与成果摘要；
  • 点击任务 ID/标题直接打开该任务详情（归档任务只读）；父需求/来源任务同样可点击跳转。

10.22 嵌套 Git 仓库兼容（gitlink / 未注册 submodule）

有些项目父仓库把子目录记录成 gitlink（mode 160000），但没有配置 .gitmodules（例如 caresy 的 caresy-api、caresy-web）。这种结构下 git worktree 检出后子目录是空的，改动也无法随父仓库合并落地，容易造成「任务显示完成但代码没进主工作区」。

Orcsy 会自动识别这类仓库并切换兼容模式：

  • 含 gitlink 的项目不使用 worktree 隔离，任务直接在项目主工作区执行；子仓库文件真实可见、可修改；
  • 该项目强制串行执行，避免多个任务同时改同一个子仓库；
  • 运行台账与审查会合并展示父仓库 gitlink 指针 + 各子仓库 git status/diff，不会只看空 diff；
  • 「待人工提交」页按仓库分组展示子仓库真实改动，可逐文件预览 diff、排除/删除临时产物；
  • 人工提交会按 子仓库先提交 → 父仓库最后提交 gitlink 指针 的顺序自动完成，可选推送；子仓库未全部推送成功时父仓库不推送。

限制：兼容模式不做 worktree 隔离/并行；子仓库提交使用各自当前分支，所有仓库共用同一条 Commit Message。适合 caresy 这类历史嵌套仓库，新建项目建议直接使用正规 submodule 或拆成独立受管项目。

10.23 合并冲突自愈

多角色小组并行开发时，多个任务的 worktree 分支可能触碰同一文件（如路由注册表）。当 Agent 的代码成果合入主分支工作区发生冲突时，Orcsy 不再直接报错，而是自动进入自愈流程：

  1. 自动标记续跑：保留 worktree 成果（不丢弃任何代码），任务标记 resume_run；
  2. 冲突同步进沙盒：主工作区未提交改动以 git apply --3way 打进 Agent 的 worktree（冲突标记 <<<<<<< 落在 Agent 可编辑的文件里）；
  3. Agent 消解冲突：同一角色下轮 re-enter 时，任务提示词会包含冲突上下文与解决指引，Agent 解决标记、重跑测试后重新完成；
  4. 限次防死循环：最多自动自愈 2 次，仍冲突才转 blocked 交人工。

自愈期间任务状态为 open（非 blocked），可在项目卡任务列表中看到续跑标记。

空 worktree 自愈兜底（0.31.0）：实测偶发（约 1/8 运行）worktree 检出后 零跟踪文件、Agent 面对空目录只能 blocked。现在任务沙盒建立完成时会校验一次 「非空基线」——若 worktree 为空而基准分支有内容，自动强制移除重建，故障对 Agent 透明。

10.24 依赖图可视化（DAG）

项目卡展开「依赖图 (DAG)」可查看任务间的依赖关系拓扑：

  • 分层布局：从无依赖的根任务起，按最长路径分层排列；
  • 状态着色：待办（蓝）/ 执行中（橙）/ 受阻（红）/ 已完成（绿）；
  • 依赖边箭头：指向被依赖的下游任务，颜色跟随目标状态；
  • 点击节点：直达任务详情（只读）。
  • 移动端横向滚动可查看完整图。

10.25 Agent 提交身份

当开启「Git 自动提交与合并」时，Agent 自动产生的 commit 可配置独立的作者身份，与人工提交区分：

  • 全局设置：「设置 → 工具与网络 → Agent 工具与访问权限」→「提交作者名 / 提交作者邮箱」；
  • 项目覆盖：项目设置 →「覆盖 Git 代码提交与合并策略」→ 填写该项目专属的作者名/邮箱（留空继承全局）。

典型用法：全局配 Orcsy Agent + orcsy@example.com，让 git log --author="Orcsy" 一眼筛出所有 Agent 产生的提交。留空则跟随环境/仓库现有 git config。

10.26 全过程日志回放

每个任务的运行详情新增全过程事件流回放：除了既有的工具调用与进度事件外，现在还记录：

  • 模型消息正文（每轮 Agent 的回复内容，含截断）；
  • 模型思考摘要（推理模型的思考内容，含截断）；
  • 计划调用清单（模型计划调用的工具名与参数摘要）；
  • 工具执行结果（完整结果文本，4KB 截断）。

在任务详情 →「运行记录」→ 点击 run_id 展开事件流即可逐条查看。事件字段已脱敏（API Key 等敏感值不出本地）。

11.2 配置备份

建议备份：

  • 数据目录（配置、技能、日志、用量）；
  • 运行台账目录（默认在数据目录下的 runs/；若在 runlog.dir 指定了其它位置，备份那个目录）；
  • 各项目的 tasks/ 和 AGENT.md；
  • 项目代码本身（用 Git 远端备份）。

config.yaml 里有 API Key，不要上传到公开仓库、不要发给别人。

内置配置备份命令（1.0 稳定化 S2）。备份内容：config.yaml + sessions.json（登录会话），归档一律 chmod 600。

# 备份到内置本地目标（config.yaml 同级 backups/）
orcsy backup-config

# 备份到指定存储目标（见下方 storage_targets 注册表）
orcsy backup-config --target my-s3

# 升级失败回滚：从本地归档恢复（当前配置自动留 config.yaml.pre-restore 兜底）
orcsy restore-config backups/orcsy-config-backup-<时间戳>.tar.gz

# 从存储目标下载归档再恢复（第二参数是远端归档文件名）
orcsy restore-config --target my-s3 orcsy-config-backup-<时间戳>.tar.gz
  • 自动备份：升级/安装新版本前会自动创建一份本地配置备份，并按 backup.target 推送到远端（推送失败不阻止升级）；
  • 备份归档含 API Key 与登录会话，与 config.yaml 同等保密等级。

存储目标在 config.yaml 的 storage_targets 注册表声明，backup.target 引用其名（local 为内置本地目标，无需声明）：

storage_targets:
  my-webdav:
    type: webdav
    url: https://dav.example.com/orcsy/   # WebDAV 目录 URL
    username: ""                          # 可选；留空 = 匿名
    password: ""                    # Basic Auth 密码
  my-s3:
    type: s3
    endpoint: https://s3.example.com      # 空 = AWS；MinIO/兼容空间填 endpoint
    bucket: orcsy-backups
    region: us-east-1
    access_key: ""
    secret_key: ""
backup:
  enabled: false          # 升级前自动备份是否也推送到远端（本地始终留一份）
  target: my-s3           # storage_targets 目标名；local = 内置本地
  keep_last: 10           # 本地保留份数

支持三种目标类型：local（本地目录）、webdav（WebDAV PUT + Basic Auth，覆盖主流 NAS/网盘）、s3（S3 兼容协议，如 MinIO、以及腾讯云 COS / 阿里云 OSS 等提供的 S3 兼容接入点；登录用 AWS Signature V4，无需额外依赖）。远程目标主机会自动加入出网白名单。也可以在看板「设置 → 数据与合规 → 备份与归档」里可视化配置存储目标与备份目标。

11.3 项目归档

把一个项目的任务快照一键打包推送到存储目标（定位是「快照分发 / 合规审计」，与 Git 远端互不替代）：

# 归档到内置本地目标（数据目录 archive/）
orcsy archive-project demo

# 归档到指定存储目标，并附带 runs/<项目> 运行台账
orcsy archive-project demo --target my-s3 --include-runs

归档内容：tasks/*.md（含 done/ 归档）+ AGENT.md + 项目记忆文档（ARCHITECTURE.md / PROJECT_NOTES.md / LONG_TERM_MEMORY.md）；--include-runs 附带运行台账。归档目标与保留份数在 config.yaml 的 archive 节配置（enabled / target / include_runs / keep_last），也可在看板「设置 → 数据与合规 → 备份与归档」配置。归档是单向快照；恢复 = 手动下载后回灌 tasks/ 与记忆文档（自动回灌后续再设计）。

11.4 迁移到另一台电脑

  1. 在新电脑安装 Orcsy；
  2. 关闭程序；
  3. 把旧电脑的数据目录复制到新电脑对应位置；
  4. 打开 config.yaml，检查 projects[].path 是否要改成新电脑的路径；
  5. 启动程序，打开看板确认项目和任务都在。

也可以用环境变量 ORCSY_DATA_DIR 把数据目录整体改到别的位置（例如移动硬盘）。

12. 常见问题与排查

12.1 看板打不开 / 端口被占用

  • 确认程序在运行（托盘图标是否还在）；
  • 默认地址是 http://127.0.0.1:5116；
  • 如果端口被别的程序占用：
    • 用配置端口启动：程序会自动换一个空闲端口，控制台会提示新端口；
    • 用 --port 显式指定：如果被占用会直接报错退出（尊重你的选择）；
  • 如果占用端口的是另一个 Orcsy 实例：本次启动会直接取消并提示「检测到已有 Orcsy 实例」，避免两个实例同时扫描/执行同一批任务；确实要另起实例请用 --port 指定不同端口；
  • 右键托盘图标「退出」会同时停止看板服务并结束 Orcsy 进程（运行中的任务按中断处理，下次启动会重置重跑）；如果退出后浏览器里还能操作，说明你启动的是另一个独立实例，请先关掉它。

12.2 任务一直「受阻」

点开任务看「Agent 处理结果」和运行日志，常见原因：

  • 模型请求失败（超时、429、500、502、503、504）：程序会自动退避重试；仍失败才标受阻；
  • AI 判断信息不足、需要人工决策；
  • 审批被拒绝或超时；
  • 测试命令不存在或环境缺少工具链；
  • 合并冲突；
  • 任务在执行期间被修改（stale_lease）：提交前二次校验发现正文/依赖/模型已变化，本次不提交；确认改动后点「重新入队」。

处理：

  1. 看日志定位原因；
  2. 修改任务描述，补充信息或缩小范围；
  3. 点「重新入队」，下一轮会优先重跑。

12.3 审批没人处理会卡死吗

不会。超过审批超时（默认 30 分钟）会自动拒绝，AI 会收到拒绝原因并调整方案或按受阻收尾。

12.4 中途关机 / 强杀进程，任务会丢吗

不会丢任务文件。执行进度会实时写进任务文件的「## 执行进度」；意外中断的任务在下次启动时会被重置回待办，重新排队。

如果中断发生在已经产生 WIP 提交或已经完成合并之后，系统会保留 worktree 和断点标记，下次从现有成果继续（任务会被标记为续跑），不会从头重跑，也不会重复提交；如果中断发生在写代码阶段（还没有 WIP 提交），未提交的改动会按原有逻辑丢弃后重跑。

12.5 国内网络拉依赖失败

按顺序尝试：

  1. 设置页「镜像源管理与测速选源」→ 测速 → 应用最快源；
  2. 在「Agent 子进程环境变量」里配 GOPROXY / PIP_INDEX_URL / npm_config_registry / HTTP_PROXY；
  3. 打开「任务启动时自动把缺失的工具目录写入用户 PATH」；
  4. 如果公司有内网镜像，在镜像源页添加并测速。

12.6 支持哪些模型

  • OpenAI 兼容协议：DeepSeek、智谱 GLM、Kimi、通义、OpenAI、Ollama、vLLM 等；
  • Anthropic 协议：Claude 官方及兼容服务。

用「获取列表」和「测试连接」验证配置。

12.7 外网 / 服务器部署要注意什么

  • 看板默认只监听 127.0.0.1，本机使用最安全；
  • 对外暴露必须设置 web.auth_password；
  • 非回环地址 + 空密码会拒绝启动；
  • 鉴权不替代 TLS，公网建议反向代理 + HTTPS；
  • 不要把 config.yaml 提交到仓库。

12.8 合并冲突 / 推送失败

  • 提交和合并由系统执行，AI 不直接操作 Git；
  • 合并冲突时会保留 arranger/<项目名> 分支，任务标受阻，等人工处理；
  • 推送失败通常是凭据问题：HTTPS 用 token，SSH 用密钥；
  • 处理完后点「重新入队」。

12.9 Windows 更新需要管理员权限吗

  • 装在用户可写目录：全程零 UAC；
  • 装在 Program Files 等系统目录：会弹一次 UAC，点「是」继续；取消则不更新，程序照常运行；
  • 更新失败会自动回滚并保留安装日志。

12.10 能不用看板，只当命令行调度器吗

可以：

orcsy run --config config.yaml          # 持续调度
orcsy run --config config.yaml --once   # 单轮，适合 Windows 计划任务 / cron

看板模式也可以加 --no-sched，只保留手动「立即扫描」。

12.11 托盘图标没出现 / 不想要托盘

  • 用 --no-tray 启动；
  • Docker 内自动关闭托盘；
  • 没有托盘不影响看板，直接访问地址即可；但系统通知也没有渠道。

12.12 任务完成后代码去哪了

  • Git 项目（默认）：改动经独立审查后增量落地主分支工作区（未提交状态），由你在「待人工提交」页确认 commit/push；
  • Git 项目（开启 commit_and_merge）：审查通过后自动提交并合并回主分支，配置了远端还会推送；
  • 非 Git 项目：直接改在项目目录里，不提交；
  • Git 项目受阻/取消：临时副本被丢弃，项目主目录不变；
  • 非 Git 项目受阻/取消：没有临时副本，Agent 已经做的修改会留在项目目录里，需要你自行检查或还原。
